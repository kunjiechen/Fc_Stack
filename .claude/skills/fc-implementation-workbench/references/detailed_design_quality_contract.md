# Detailed Design Quality Contract

## 1. 目的

本文件定义“什么叫一份好的 FC 详细设计”。

它不是输出模板，也不是实现细节清单，而是详细设计生成与评审的质量合同。

后续无论由人工编写还是由 bundle 自动渲染，最终文档都应满足这里的要求。

## 2. 核心定位

详细设计必须是：

- 面向实现
- 面向编码起步
- 面向功能方案、接口、内部接口、配置、运行态、故障处理
- 面向“减少开发猜测”

详细设计不是：

- 需求文档重写
- 架构文档复述
- 芯片手册翻译
- 伪代码堆砌
- 生成过程说明书
- 为了显得完整而无限加章节

## 3. 总体质量标准

一份合格的详细设计，至少要满足下面七项。

### 3.1 可实现

开发拿到文档后，不应再猜这些核心问题：

- FC 采取什么实现方案
- 外部接口怎么组织
- 内部接口为什么这样拆
- 依赖接口怎么接
- 配置参数在哪里控制
- 运行时变量放哪里
- fault / DET 怎么分界
- MemMap 怎么落

### 3.2 可追踪

文档中的关键设计必须能回到上游对象：

- requirement
- architecture freeze
- 项目约束
- 待确认项

如果正文中出现重要结论，却无法解释来源，则视为质量不足。

### 3.3 粒度合适

文档既不能过轻，也不能过重。

过轻的表现：

- 只写“接口作用”，不写执行步骤
- 只列内部接口名，不写职责和调用关系
- 只说有 fault，不说检测/响应/恢复
- 只说有 cfg，不说 formal / reserved / pending

过重的表现：

- 把芯片手册寄存器行为逐段复述
- 把代码语句级别内容硬写进流程图
- 为轻量模块硬造复杂状态机
- 把一个完整动作拆成大量低价值小接口

### 3.4 一致性强

文档不得和上游 freeze 漂移。

必须保持：

- external interface 与 architecture 一致
- dependency interface 与 architecture 一致
- reserved / pending_confirm 表达一致
- 关系引用不指向未定义对象

### 3.5 正文不暴露内部生成痕迹

skill 内部可使用 grounding、bundle、conf evidence、validation objects。

但正文中不应直接呈现：

- grounding 基线模块名单
- `Conf_*` 证据条目
- bundle 字段名
- “本段由生成器推断”之类的内部痕迹

这些内容应服务生成，不应污染交付文档。

### 3.6 待确认信息不单列成正文主章节

不能把实现方案写成“假设”。

正文应明确区分：

- 已确认设计结论
- reserved 能力
- 项目约束
- 仍需项目确认的信息

若仍存在少量待确认内容，应吸收进相关设计章节或覆盖表备注中，而不是单列“待确认项”主章节。

### 3.7 面向项目风格

详细设计应优先体现公司和项目的真实工程风格，而不是“教科书平均答案”。

因此：

- 多核、MainFunction、Callout 风格必须和本地工程样本一致
- 复杂模块应强化状态机、故障分类、框架关系
- 简单模块应允许轻量表达，不强加状态机

## 4. 章节质量要求

### 4.1 必须强写的章节

这些章节不能只做模板填空，必须有明确设计判断。

- `1. FC概述`
- `4. 功能设计`
- `7. 外部接口设计`
- `8. 内部接口设计`
- `9. 依赖接口与Callout设计`
- `12. DET设计`
- `13. 故障处理设计`
- `15. 配置宏参设计`
- `18. 架构与详细设计覆盖表`

### 4.2 可以弱化但不能乱写的章节

这些章节允许根据模块复杂度轻量化，但不能编造。

- `6. 单核/多核框架设计`
- `11. 状态机设计`
- `14. 运行时变量设计`

### 4.3 可以模板化或 Empty/Reserved 的章节

这些章节允许标准化表达，但必须说明为什么为空或保留。

- 无复杂状态机时，状态章节可弱化
- 无跨核共享对象时，同步点表可为空

## 5. FC 概述章节最低要求

至少要说明：

- FC 简洁功能介绍
- 所属层级
- 实现方案概览
- 与周期任务或触发机制的关系

不应只写抽象职责标签。

## 6. 外部接口章节最低要求

每个 formal external interface 至少要说明：

- prototype
- purpose
- sync/reentrancy
- 基本约束
- 子功能拆分
- 执行步骤
- 参与内部接口
- 与 dependency 的关键关系

如果接口逻辑非平凡，只写一个总说明表格不算合格。

## 7. 内部接口章节最低要求

内部接口设计不能只是函数清单。

至少要回答：

- 为什么存在这个内部接口
- 为什么和别的内部接口归并或不归并
- 它由谁触发
- 它读写什么
- 它和 external/dependency 的关系是什么

内部接口名称应保持规范全称，不应只展示脱离上下文的简称。

## 8. 依赖接口章节最低要求

依赖接口不能只写“调用某个 callout”。

至少要说明：

- 原型
- 谁实现
- 为什么这个依赖存在
- 基本约束
- 关联接口
- 失败对 FC 的影响边界

## 9. DET 与 Fault 的质量边界

DET 和 fault 必须严格区分。

- DET 负责开发期调用防御
- fault 负责运行期异常行为

不允许：

- 用 DET 代替 fault 设计
- 只写“记录故障”而不写响应和恢复
- 把复杂 fault 设计压缩成一句话

## 10. 状态机质量边界

只有在模块真的有阶段、模式、运行态演进时，才应强化状态机。

复杂模块应重点体现：

- 软件状态机
- 芯片状态机
- 状态关系
- 跳转条件
- 各状态动作

轻量模块不允许为了看起来完整而强行构造复杂状态机。

## 11. 流程图质量边界

流程图必须表达“步骤”和“关系”，不能表达“代码”。

允许：

- 执行阶段
- 条件分支
- 失败路径
- 状态切换
- 软硬件接口关系

不允许：

- 变量名堆砌
- 数组下标
- 逐句伪代码化

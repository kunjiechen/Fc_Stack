# AURIX2G 参考工程学习提炼

## 1. 目的与边界

本文档基于参考工程 `FcStack-main-2/src/FcStackBase/AURIX2G` 做学习提炼，目标不是复述工程实现，而是抽出后续可迁移到 `fc-implementation-workbench` 的详细设计方法、代码组织方法和公司化规范要点。

约束如下：

- 正式 skill 不直接包含该工程代码或具体实现。
- 正式 skill 只吸收可复用的方法、结构、模板、检查规则。
- 工程中的芯片寄存器细节、项目特定配置值、具体信号表，不作为通用规则固化。

## 2. 工程整体架构观察

### 2.1 顶层目录分层

该工程不是简单按功能文件堆叠，而是按平台与职责分层：

- `BootCtrl`
  - 启动控制、各核启动入口、早期平台初始化。
- `BootM`
  - Boot manager，负责启动管理逻辑。
- `Bsw_Gp`
  - 通用基础软件能力，包含 `Gp_EcuM`、`Os/TimeOs` 等。
- `BswSys_Gp`
  - 系统级状态与控制模块，如 `Gp_SysState`、`Gp_RstM`、`Gp_WkUpSrcM/P`、`Gp_EcuStpShdn`。
- `IoMcu`
  - MCU 直连 IO 抽象层，如 `Gp_IoMcuAdc`、`Gp_IoMcuDio`、`Gp_IoMcuIcu`、`Gp_IoMcuPwm`。
- `IoSigSrv`
  - 信号服务层，对底层原始 IO 进一步封装为业务可用信号。
- `Cdd`
  - 复杂驱动或定制器件驱动，如 `Gp_Pwm3hb`、`Gp_06_Adc3ph`、`Gp_TimeRecord`。
- `Mcal_Aurix2G`
  - MCAL 和厂商底层驱动。
- `Mcal_Aurix2G_Gp`
  - 针对芯片平台补充的通用平台库、异常、MPU、SCR、PMS 等。
- `RtMon`
  - 运行时监控，如任务耗时、CPU 负载、栈、CSA。
- `SafeTpack`
  - 安全包、自检、监控和测试。
- `Conf`
  - 所有模块配置、集成层配置、MemMap、链接脚本、OS 任务编排。

### 2.2 分层关系

从 coding 角度可以提炼成下面的可复用分层模型：

1. `Chip/MCAL 层`
   - 直接寄存器、MCAL 驱动、平台通用库。
2. `IO 抽象层`
   - 对 ADC/DIO/PWM/ICU 等进行统一访问和基础校验。
3. `Signal/Device 层`
   - 将原始 IO 变成可用信号，或对复杂外设做专用封装。
4. `System Service 层`
   - 状态机、唤醒、复位、停机、调度、监控。
5. `Boot/Init/Safety 层`
   - 启动、多核同步、安全自检、异常处理。
6. `Configuration/Integration 层`
   - 模块配置、任务配置、内存布局、跨模块集成。

这个分层模型适合直接转化为详细设计的总章节结构。

## 3. 代码组织的“标准模块形态”

工程里大量模块遵循统一形态，这一点非常适合抽成 skill 规则。

### 3.1 典型模块文件族

常见模块由以下文件组成：

- `Module.c/.h`
  - 对外服务接口和主逻辑。
- `Module_Types.h`
  - 内部和外部共享类型、枚举、函数指针、运行时结构。
- `Module_Cfg.h`
  - 编译配置宏、功能开关、尺寸定义。
- `Module_CfgData.h`
  - `extern` 声明的配置数据容器。
- `Module_Cfg.c`
  - 具体配置实例。
- `Module_Callout.h/.c`
  - 依赖注入/适配层接口，隔离平台或上层差异。
- `Module_Internal.h`
  - 内部接口，仅在模块内或近邻使用。
- `Module_MemMap.h`
  - 内存段映射。

### 3.2 对 skill 的直接启发

详细设计不应只写“模块 A 提供接口 x”，还要强制给出该模块的文件组织建议：

- 是否需要 `Types`。
- 是否需要 `Cfg/CfgData`。
- 是否需要 `Callout`。
- 是否需要 `Internal`。
- 运行时变量和常量配置分别放哪里。
- 哪些变量需要 `MemMap` 分段。

也就是说，详细设计输出要达到“程序员知道要建哪些文件”的粒度。

## 4. 软件分层与职责边界经验

### 4.1 业务逻辑不直接贴寄存器

`Gp_Pwm3hb` 这类 CDD 模块自身负责参数转换和行为规则，但真正的寄存器写入通过 `Callout` 完成。  
结论：

- 模块本体负责算法、约束、接口协议。
- 芯片/板级差异通过 `Callout` 或配置注入。
- 详细设计里要明确“主模块逻辑”和“平台适配点”的分界。

### 4.2 配置与运行时严格分开

例如 `Gp_IoMcuAdc`：

- `Cfg.c` 中放每核信号映射、寄存器地址、组配置。
- `c` 文件中放每核运行时 buffer。
- `CfgData.h` 只对外暴露配置容器。

结论：

- 配置态对象要可审查、可替换、可生成。
- 运行态对象要按核心、生命周期、访问域单独定义。
- 详细设计应明确每个数据对象属于“配置态 / 运行态 / 保留态 / NoClear 态”中的哪类。

### 4.3 系统级模块与设备级模块分开

`Gp_SysState`、`Gp_RstM`、`Gp_WkUpSrcM/P` 负责系统治理；  
`Gp_IoMcuAdc`、`Gp_Pwm3hb` 负责能力实现。

结论：

- 详细设计必须区分“系统控制模块”和“资源/设备模块”。
- 系统模块优先描述状态、流程、策略、时序。
- 设备模块优先描述接口、配置、转换、访问约束。

## 5. 多核架构与调度设计经验

### 5.1 多核不是靠 if 判断，而是结构先分开

工程中多核支持非常显式：

- `Gp_EcuM` 有 `Core0Init` 到 `Core5Init`。
- `TimeOs` 有 `TimeOs_CoreXTask.c`。
- `Gp_TaskTimeMon`、`Gp_IoMcuAdc` 等按 core 建 runtime buffer。
- `Conf/Conf_Intg/Os/BaseTask` 按核拆任务文件。

这说明其设计原则是：

- 每核入口显式化。
- 每核运行数据显式化。
- 每核任务编排显式化。
- 共享同步点显式化。

### 5.2 多核同步方法

`Gp_EcuM` 使用共享数组 `Gp_EcuM_infSyncEvent_lau32[]` 做启动同步：

- 各核到达同步点后置位事件。
- 主核等待所有事件完成再进入下一阶段。

这是一种很重要的设计抽象：

- `初始化阶段同步`
- `运行阶段通常分治`
- `共享资源通过少量同步点收口`

后续 skill 在设计多核模块时，应优先输出：

1. 每核职责表
2. 每核初始化顺序
3. 同步点表
4. 跨核共享变量表
5. 共享数据一致性策略

### 5.3 调度结构经验

`TimeOs` 采用 `Core + 周期槽` 的固定组织方式：

- `InitTask`
- `Hp1ms`
- `Nm5ms`
- `Nm10msA`
- `Nm10msB`
- `Nm100ms`

而且每个周期槽内通常有三类内容：

1. 存活计数/活跃度计数
2. 运行监控钩子
3. 真正业务调用

这意味着详细设计中“任务设计”建议固定输出以下内容：

- 核 ID
- 周期
- 优先级类别
- 入口函数名
- 调用模块列表
- 监控动作
- Alive counter 或节拍计数策略

## 6. 状态机设计经验

### 6.1 `Gp_SysState` 的落地方式值得复用

该模块不是散乱 `switch-case`，而是：

- `Types.h` 中先定义状态、阶段、切换路径枚举。
- 定义 `CheckFunc_pf` 和 `ActionFunc_pf`。
- 定义 `SwitchFuncIndex` 和 `SwitchInfo`。
- `MainFunction()` 中按当前状态扫描对应切换条件。

这是典型的“表驱动状态机 + 条件函数 + 动作函数”模式。

### 6.2 对详细设计的启发

状态机块应至少输出：

- 状态枚举
- 阶段枚举
- 切换路径枚举
- 条件检查函数清单
- 动作函数清单
- 每个状态可触发的切换范围
- 状态记录/追踪机制

而不是只放一张状态图。

### 6.3 状态记录机制

`Gp_SysState` 还设计了 recorder：

- 记录 phase/state
- 记录时间戳
- 记录 boot 到 app init 的连续过程

这说明公司风格不是只关注“当前状态”，还关注：

- 可追踪
- 可回溯
- 可结合启动链路分析

因此 skill 应默认考虑：

- 是否需要状态变化记录
- 是否需要时间戳
- 是否需要保留在 NoClear 区域

## 7. 故障、复位与安全治理经验

### 7.1 开发期错误与运行期错误分开

例如 `Gp_SysState`、`Gp_WkUpSrcM` 都有 `DevErrMaskType`。  
这类错误用于：

- 未初始化
- 参数越界
- 空指针
- 地址不对齐

结论：

- 详细设计需单列 `DET/开发期错误检查`。
- 不能把所有错误都笼统称为 fault。

### 7.2 运行期保留数据与复位策略非常关键

`Gp_RstM` 提供：

- `NoClear` 数据记录
- 双保存地址
- 错误复位计数
- 安全态信息
- 复位前后状态承接

说明该工程把“复位不是结束，而是系统行为的一部分”。

因此详细设计文档中故障与复位块至少要分为：

1. 运行期错误检测
2. 降级或保护动作
3. 复位触发条件
4. 复位后状态恢复/数据继承
5. NVM 持久化策略

### 7.3 运行监控是系统骨架，不是附属品

`RtMon` 中包含：

- `Gp_TaskTimeMon`
- `Gp_StackMonitor`
- `Gp_CsaMonitor`
- `Gp_CpuLoadMonitor`

而且这些监控已经进入 `TimeOs` 周期任务。

结论：

- 对公司化详细设计来说，监控和可观测性要成为标准章节。
- 至少要设计任务耗时、栈使用、关键状态可观测对象。

## 8. 接口设计经验

### 8.1 外部接口风格

大多数模块外部接口遵循：

- `Init`
- `MainFunction`
- `Get/Set`
- `PerformXxx`
- `RecordXxx`

接口头注释固定包含：

- Sync/Async
- Reentrancy
- 参数方向
- 返回值
- 描述

这说明详细设计里的接口表不能只写“函数名 + 说明”，还应带：

- 同步属性
- 重入属性
- 调用上下文
- 失败返回
- 前置条件

### 8.2 内部接口风格

内部接口通过 `Internal.h` 控制暴露范围，典型用途：

- 状态设置
- 模块内动作函数
- 内部工具函数

说明详细设计要明确：

- 哪些接口开放给外部模块
- 哪些仅开放给同模块子文件
- 哪些为静态局部函数

### 8.3 `Callout` 是关键抽象层

从多个模块看，`Callout` 不是可有可无，而是工程标准手段：

- 隔离芯片/板级差异
- 隔离项目集成差异
- 提供上层依赖注入

后续 skill 应优先识别以下场景并建议生成 `Callout`：

- 直接寄存器访问
- MCU/项目差异逻辑
- 外部模块回调依赖
- 特定信号获取方式可变

## 9. 配置、变量与内存布局经验

### 9.1 运行变量设计

工程中的运行变量有几个稳定规律：

- 每核独立 runtime buffer
- 运行态结构体集中定义
- `static` 本地变量优先
- 共享变量仅在必要时全局暴露

建议详细设计时将变量按以下维度建表：

- 名称
- 所属模块
- 所属核
- 类别：输入态 / 中间态 / 输出态 / 状态态 / 监控态
- 生命周期
- 读写方
- 是否跨核
- 是否 NoClear

### 9.2 配置变量设计

工程里的配置对象主要分三层：

1. `Cfg.h`
   - 宏与尺寸
2. `CfgData.h`
   - 配置实例声明
3. `Cfg.c`
   - 实际配置值、表项、映射关系

建议 skill 输出时也按这三层组织，而不是把所有配置混在一张表中。

### 9.3 MemMap 是正式设计的一部分

工程大量使用：

- `CLEAR_FAR_DATA`
- `CONST_FAR_DATA`
- `NO_CLEAR_FAR_DATA`
- `CODE_START/STOP`
- 甚至按 `CORE0~CORE5` 分段

这意味着对 FC 详细设计来说，内存归属不是实现细节，而是设计对象。  
因此后续详细设计要增加：

- 变量内存段归属
- 是否需 NoClear
- 是否需 NOCACHE
- 是否按 core 分段

## 10. 可直接沉淀为 skill 的分块抽取规则

### 10.1 软件架构块

输入抽取：

- 目录结构
- 模块职责
- 模块依赖
- 平台与业务边界

输出要求：

- 系统层次图
- 模块职责表
- 依赖方向图
- 哪些为平台公共模块，哪些为项目业务模块

### 10.2 软件分层块

抽取方法：

- 识别 `MCAL/IoMcu/IoSigSrv/Cdd/BswSys/Bsw/Boot/RtMon/SafeTpack/Conf`
- 提炼标准层级与调用方向

输出要求：

- 分层说明
- 每层输入输出
- 不允许的跨层访问

### 10.3 状态机块

抽取方法：

- 先找枚举
- 再找切换条件函数
- 再找动作函数
- 再找主循环调度入口

输出要求：

- 状态枚举
- 切换路径
- 条件检查
- 动作清单
- 状态记录策略

### 10.4 故障处理块

抽取方法：

- 提取 `DevErrMask`
- 提取运行期错误码
- 提取 reset/no-clear/nvm 接口
- 提取监控模块

输出要求：

- 开发期错误
- 运行期错误
- 降级动作
- 复位策略
- 保留数据策略

### 10.5 单核/多核结构块

抽取方法：

- 找 `CoreXInit`
- 找 `CoreXTask`
- 找 per-core runtime buffer
- 找同步变量或同步 API

输出要求：

- 核职责表
- 初始化阶段表
- 周期任务表
- 核间同步表
- 核间共享资源表

### 10.6 外部接口块

抽取方法：

- 统计 `Init/MainFunction/Get/Set/Perform/Record`
- 提取参数方向和同步属性

输出要求：

- API 表
- 前置条件
- 返回码
- 调用关系

### 10.7 内部接口与封装块

抽取方法：

- 识别 `Internal.h`
- 识别 `static` 局部函数
- 识别 `Callout`

输出要求：

- 内部接口表
- 平台适配点
- 依赖注入点
- 可替换实现点

### 10.8 实时变量与配置变量块

抽取方法：

- 识别 runtime 结构
- 识别 cfg 结构
- 识别 no-clear 与 monitor 对象

输出要求：

- 运行变量表
- 配置项表
- 生命周期
- 内存段归属

## 11. 公司化规范要点

从工程中可观察出的“公司化”特征如下：

### 11.1 文档化头注释统一

文件头统一包含：

- Namespace
- Class
- Name
- ArchiVer / FcVer
- Author
- 是否允许用户修改
- History

建议正式 skill 将这些作为默认文档元数据输出。

### 11.2 接口说明统一

函数注释统一包含：

- Function Name
- Service ID
- Sync/Async
- Reentrancy
- Parameter[in/out/inout]
- Return Value
- Description

建议详细设计模板直接对应这些字段。

### 11.3 架构版本与代码版本分离

工程中常见：

- `ArchiVer History`
- `FcVer History`

说明其管理思想是：

- 架构演进和代码版本演进分开管理

这一点非常适合引入详细设计文档：

- 设计版本
- 实现版本
- 适用平台

### 11.4 “可配置、可集成、可适配”优先

公司风格明显偏好：

- 配置表
- Callout
- MemMap
- per-core 分段
- 统一命名

所以后续 skill 不应生成“简化版 demo 设计”，而应优先生成：

- 有配置边界
- 有平台适配点
- 有可观测性
- 有错误策略

的正式设计。

## 12. 对后续详细设计 skill 的直接建议

### 12.1 不要直接从文档生成 md，先生成中间设计模型

建议先抽成结构化对象：

- modules
- layers
- tasks
- cores
- state_machines
- faults
- interfaces
- runtime_variables
- configs
- memory_sections
- traceability

然后再生成 markdown。

### 12.2 skill 输出必须达到“可编码”粒度

至少要给到：

- 文件族建议
- 模块职责
- 对外接口
- 内部接口
- 调度入口
- 状态机
- 变量表
- 配置表
- 故障处理
- 多核映射
- 监控设计

### 12.3 skill 应区分“工程经验”与“项目实例”

应该保留的：

- 分层方法
- 状态机组织方式
- 多核组织方式
- 配置与运行态分离方法
- Callout 抽象方式
- MemMap/NoClear/监控等公司化要求

不应硬编码的：

- 具体寄存器地址
- 具体信号 ID
- 具体 core 的 ADC 通道表
- 具体项目的 wakeup 条件值

## 13. 结论

这个 AURIX2G 工程非常适合作为详细设计 skill 的“学习样本”，因为它覆盖了：

- 软件架构与软件分层
- 启动与多核同步
- 周期调度
- 状态机设计
- 故障/复位/NoClear 数据
- 接口分层
- 配置组织
- MemMap 和监控体系

对后续 skill 来说，最有价值的不是具体模块功能，而是以下设计语法：

- `模块 = 服务接口 + 类型定义 + 配置 + Callout + MemMap + 运行态`
- `多核 = 显式入口 + 显式数据 + 显式任务 + 显式同步`
- `状态机 = 枚举 + 条件函数 + 动作函数 + 配置表 + 记录机制`
- `故障治理 = 开发期错误 + 运行期错误 + 监控 + 复位 + 保留数据`
- `公司化 = 统一头注释 + 统一 API 注释 + 架构/代码双版本 + 可配置可适配`

这套方法可以直接作为后续 `fc-implementation-workbench` 的设计经验底座。

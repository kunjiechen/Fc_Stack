## 3. 单核代码框架规则

### 3.1 单核模块适用场景

适合以下场景：

- 模块只运行在单个核
- 无核间同步需求
- 运行时数据不跨核共享
- 任务入口只挂在一个周期槽

### 3.2 推荐文件族

单核模块建议默认生成：

- `Module.h`
- `Module.c`
- `Module_Types.h`
- `Module_Cfg.h`
- `Module_CfgData.h`
- `Module_Cfg.c`
- `Module_Callout.h/.c`
- `Module_MemMap.h`

若模块复杂度较高，再增加：

- `Module_Internal.h`

### 3.3 单核模块代码框架

建议统一包含：

1. 文件头注释
2. 头文件引用
3. 宏定义
4. 类型定义
5. 全局运行时变量
6. 静态局部变量
7. 静态局部函数声明
8. `InitMemory`
9. `Init`
10. `MainFunction`
11. `Get/Set/Service API`
12. 静态辅助函数

### 3.4 单核设计输出要求

详细设计或 skill 输出时，至少应给到：

- 初始化顺序
- 周期执行入口
- 配置容器
- 运行时结构体
- 内部函数列表
- 外部 API 表

## 4. 多核代码框架规则

### 4.1 多核模块适用场景

适合以下场景：

- 资源按核分配
- 任务按核执行
- 数据采集或监控天然按核切分
- 启动需要同步
- 平台要求每核独立入口

### 4.2 多核代码组织核心模式

从参考工程提炼出的主模式：

- `Core0Init/Core1Init/...`
- `Core0Task/Core1Task/...`
- 每核 runtime buffer
- 每核 config container
- 跨核共享同步对象

### 4.3 多核模块必须回答的 6 个问题

设计时必须明确：

1. 每个 core 的职责是什么
2. 每个 core 的初始化顺序是什么
3. 每个 core 的任务周期是什么
4. 哪些变量是 per-core 的
5. 哪些变量是共享的
6. 需要哪些同步点

### 4.4 多核代码框架建议

对多核模块，建议优先采用下面的组织方式：

- 对外接口仍然是一套模块 API
- 内部运行时按 core 拆容器
- 通过 `cfgCont[core]` 和 `rtCont[core]` 访问当前核对象
- 若各核初始化步骤明显不同，则显式暴露 `CoreXInit`

### 4.5 多核共享数据设计规则

共享数据不应随意出现，建议只允许三类：

- 启动同步标志
- 核间状态同步对象
- 明确声明的共享监控/诊断对象

共享数据必须在详细设计中标出：

- 谁写
- 谁读
- 写入频率
- 一致性要求
- 是否需要 `volatile`
- 是否放 `NOCACHE` / 特定内存段

## 5. `DET` 处理流规则

### 5.1 `DET` 的定位

`DET` 主要用于开发期和接口使用期保护，不等同于运行期 fault。

建议将错误分两层：

- `DET/DevErr`
  - 未初始化
  - 空指针
  - 参数越界
  - 状态非法
  - 地址非法
- `RuntimeErr/Fault`
  - 采样失败
  - 通信失败
  - 硬件故障
  - 监控超时
  - 功能异常

### 5.2 `DET` 代码结构建议

每个模块建议具备：

- `DevErrMaskType`
- `InitStatusType`
- 统一 `CheckInit`
- 统一 `CheckPtr`
- 统一 `CheckRange`
- 可选 `LogDevErr`

### 5.3 `DET` 处理顺序

推荐顺序：

1. 检查模块是否初始化
2. 检查输入指针
3. 检查参数范围
4. 检查运行上下文是否合法
5. 记录开发期错误
6. 返回 `E_NOT_OK` 或直接退出

### 5.4 `DET` 在详细设计中的输出要求

每个外部 API 都应给出：

- 前置条件
- 入参检查项
- `DET` 错误类型
- 失败返回

## 6. `Cfg` 配置体系规则

### 6.1 三层配置结构

推荐固定三层：

- `Cfg.h`
  - 功能开关、尺寸、模块宏、核数、表项数量
- `CfgData.h`
  - `extern` 声明配置对象
- `Cfg.c`
  - 配置实例、映射表、函数指针绑定表、硬件地址表

### 6.2 哪些内容应该放 `Cfg.c`

应放入：

- 信号映射
- 寄存器地址映射
- 每核配置表
- 状态机切换表
- 函数指针表
- 依赖接口映射
- 监控对象配置

不应放入：

- 周期变化的运行态值
- 瞬态缓存
- 中间计算结果

### 6.3 `Cfg.c` 的抽取原则

建议优先识别以下“稳定对象”，放入配置：

- 编译后不变
- 与项目集成强相关
- 与硬件连接强相关
- 与功能策略选择强相关
- 需要评审和追踪

### 6.4 per-core 配置规则

若模块多核运行，应优先设计：

- `cfgCont[core]`
- 每核局部配置表
- 全局配置容器索引

而不是写成大块 `if(core==x)` 的逻辑。

## 7. 状态机代码设计规则

### 7.1 推荐状态机风格

优先采用：

- 枚举定义状态
- 枚举定义切换路径
- 条件函数独立
- 动作函数独立
- `MainFunction` 扫描切换
- 可选 recorder 记录变化

### 7.2 不推荐的写法

尽量避免：

- 一个大函数里嵌套过深的 `switch + if`
- 条件判断和动作逻辑揉在一起
- 状态枚举与状态切换关系分散在多个文件且无统一表

### 7.3 状态机代码骨架

建议模块中至少定义：

- `StateType`
- `SwitchType`
- `SwitchConditionFuncType`
- `ActionFuncType`
- `SwitchInfoType`
- `SetState`
- `GetState`
- `MainFunction`

### 7.4 状态机切换规则

推荐采用：

- 当前状态只扫描本状态允许的切换集合
- 每次 `MainFunction` 最多只发生一次切换
- 状态变更时统一记录
- 状态动作要可审查、可测试

### 7.5 状态机详细设计输出要求

至少输出：

- 状态枚举表
- 切换表
- 条件函数表
- 动作函数表
- 状态记录机制
- 异常状态/降级状态说明

## 8. 内部函数设计规则

### 8.1 内部函数抽取的核心原则

当前工程可以提炼出以下原则：

1. 对外协议与内部细节分开
2. 条件检查与动作执行分开
3. 配置访问与运行处理分开
4. 平台差异与业务规则分开
5. 通用流程与项目适配点分开
6. 每核实例数据访问与通用逻辑分开

### 8.2 内部函数分类

建议按以下类型设计内部函数：

- 参数检查函数
- 初始化检查函数
- 配置获取函数
- runtime 获取函数
- 条件判断函数
- 动作执行函数
- 数据转换函数
- 记录函数
- 监控辅助函数
- 平台适配辅助函数

### 8.3 什么时候放 `static`

满足以下条件应优先 `static`：

- 只被当前 `.c` 使用
- 不需要跨文件复用
- 属于局部步骤或局部保护逻辑

### 8.4 什么时候放 `Internal.h`

满足以下条件可放 `Internal.h`：

- 同模块多个 `.c` 文件共享
- 不希望暴露给模块外部
- 需要为状态机动作、核心内部服务留接口

### 8.5 什么时候放 `Callout`

满足以下条件应放 `Callout`：

- 依赖硬件寄存器或外设
- 与平台、芯片、项目适配相关
- 依赖外部模块回调
- 可能被不同项目替换

## 9. 运行时变量设计规则

### 9.1 运行时变量分类

建议详细设计中强制把 runtime 变量分为：

- 输入态
- 状态态
- 中间计算态
- 输出态
- 监控态
- 故障态
- 保留态

### 9.2 runtime 设计原则

从工程中可归纳出：

- runtime 尽量模块内聚
- 每核分区优先
- 运行态与配置态分离
- 共享变量最少化
- 监控态也视为正式运行态
- 特殊生命周期变量单独标识

### 9.3 变量表最低要求

建议每个详细设计块至少给出：

- 变量名
- 类型
- 所属模块
- 所属核
- 类别
- 初值
- 写方
- 读方
- 周期
- 是否 NoClear
- 是否跨核

### 9.4 `NoClear` 变量设计规则

适合进入 `NoClear` 的变量：

- 复位前后要继承的数据
- 状态追踪记录
- 安全态或故障恢复相关信息
- 复位原因与错误计数

不建议进入 `NoClear` 的变量：

- 普通周期缓存
- 可重新计算的中间量
- 无恢复价值的临时变量

## 10. 故障处理设计规则

### 10.1 故障处理的结构建议

建议分为五层：

1. 故障检测
2. 故障确认
3. 故障响应
4. 故障恢复
5. 故障留痕

### 10.2 故障处理与 `DET` 分界

建议明确：

- `DET` 解决“接口用错了没有”
- `Fault` 解决“系统运行出问题了没有”

不要让运行期 fault 直接复用 `DET` 语义。

### 10.3 故障处理代码骨架建议

建议具备：

- 故障状态结构体
- 故障检测函数
- 故障确认/去抖函数
- 故障动作函数
- 故障恢复函数
- 故障记录接口
- 必要时复位接口

### 10.4 故障设计输出要求

详细设计至少要写清：

- 故障来源
- 检测条件
- 确认条件
- 降级动作
- 复位条件
- 恢复条件
- 记录位置

### 10.5 当前能做到的程度

基于现有学习，已经能设计：

- 故障处理框架
- 故障状态对象
- 故障检测入口
- 故障记录方案
- `NoClear/NVM/Reset` 衔接点

仍需要项目补充的：

- 阈值
- 定时
- 安全等级
- 故障优先级
- 降级矩阵

## 11. `Callout` 与适配层设计规则

### 11.1 `Callout` 的作用

`Callout` 是当前工程里非常关键的隔离层，主要用来：

- 隔离寄存器访问
- 隔离不同芯片平台差异
- 隔离项目集成差异
- 隔离特殊信号来源

### 11.2 详细设计何时强制生成 `Callout`

满足任一条件建议强制生成：

- 访问硬件寄存器
- 访问厂商特定 API
- 依赖外部模块且接口不稳定
- 存在项目差异点

### 11.3 `Callout` 设计输出要求

需要明确：

- 调用方向
- 输入输出参数
- 是否同步
- 是否可替换
- 默认实现归属

## 12. `MemMap` 与内存段设计规则

### 12.1 `MemMap` 不是实现细节

从当前工程看，内存段设计已经是架构级约束，不能忽略。

设计时至少要区分：

- `CODE`
- `CLEAR_DATA`
- `CONST_DATA`
- `NO_CLEAR_DATA`
- `NOCACHE`
- `per-core section`

### 12.2 哪些对象需要独立段

建议重点关注：

- 每核运行时 buffer
- 同步共享对象
- `NoClear` 恢复对象
- 大型 const 配置表
- 监控对象

## 13. 代码生成前的最小检查清单

在基于 skill 生成代码前，至少检查：

1. 这是单核还是多核模块
2. 是否需要 `Callout`
3. 是否需要 `Cfg.c`
4. 是否需要 `Internal.h`
5. 是否需要状态机
6. 是否需要 `DET`
7. 是否需要故障处理
8. 是否需要 `NoClear`
9. 是否需要 per-core runtime
10. 是否需要监控对象

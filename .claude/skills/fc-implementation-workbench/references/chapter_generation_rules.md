# Chapter Generation Rules

## 1. 目的

本文件定义详细设计各章节"怎么写"。

它补的是写作与展开规则，而不是字段 schema。

适用对象：

- 人工编写详细设计
- bundle 驱动的 markdown 渲染器
- 详细设计 review

## 2. 总体写作规则

### 2.1 先方案，后展开

每一章应先说明该章的设计结论或实现方案，再展开细节。

### 2.2 先结构，后叙述

优先使用：

- 表格
- 分步骤
- 关系图
- 功能框图
- 接口框图

避免大段无结构 prose。

### 2.3 先实现约束，后背景说明

详细设计优先回答：

- 开发怎么做
- 为什么这样做
- 哪些边界不能越

而不是先长篇介绍背景。

### 2.4 少写空话

出现以下表达要谨慎：

- 正常处理
- 合理管理
- 完成控制
- 进行优化
- 满足需求

这些如果不能落到具体动作或结构上，就应删掉或细化。

### 2.5 正文不展示内部生成痕迹

正文禁止直接出现：

- grounding 模块名单
- `Conf_*` 证据条目
- bundle 字段名
- 生成器 / 推断器 / schema 之类内部用语

## 3. 章节级规则

## 3.1 `1. FC概述`

### 目标

快速说明模块是谁、干什么、采取什么实现方案。

### 必写

- FC 名称
- 当前软件层级
- 核心职责（中文完整段落）
- 运行模型（同步/异步请求-周期处理/纯事件驱动/混合）
- 单核/多核
- 实现方案（中文完整段落；概要描述三层接口模型、核心设计决策）

### 建议

- 用 3 到 5 条描述功能范围和方案，不要只写标签

### 不要写

- 大段芯片原理背景
- 重复需求列表

## 3.2 `2. 设计输入`

### 目标

说明这份详细设计建立在哪些真实输入之上。

### 必写

- 需求文档
- 架构文档
- 芯片约束
- 平台约束
- 编码规范

### 禁止

- 展示 grounding 基线模块名
- 展示 `Conf_*` 证据条目
- 展示 bundle 内部对象名

## 3.3 待确认信息处理规则

### 规则

- 默认不单列 `待确认项` 主章节
- 仍需确认的信息应落入相关设计章节
- 配置开放边界类问题优先放入 `11. 配置参数设计`
- 框架部署类问题优先放入 `3. 功能设计` 或 `5. 单核/多核框架设计`
- 覆盖缺口和未完全承接项可放入 `14. 架构与详细设计覆盖表` 的备注
- 不允许把实现方案写成"假设"

### 设计增量溯源规则

配置宏参、配置类型字段、运行变量、运行参数类型字段中，凡需求和架构中不存在的、由详细设计过程自行增加的项（即 Source/设计依据 标注为 `design-addition` 的项），必须满足：

- 在 Source/设计依据 列标注 `design-addition (Rx)`，其中 `Rx` 为 §14 风险与待确认项中对应的评审项索引
- 在 §14 中为每个设计增量建立对应的评审项，说明"为何需要此增量"和"不采纳的后果"
- 裸标签 `design-addition` 未关联评审项的视为设计不完整
- 此规则适用于：配置宏参（§11.1 Source 列）、配置类型字段（§11.2.1 设计依据列）、运行变量（§10.1 设计依据列）、运行参数类型字段（§10.2.1 设计依据列）

## 3.4 `3. 功能设计`

### 目标

说明这份详细设计的整体功能方案和架构框架思想。

### 必写

- 功能设计说明（中文完整段落；核心设计决策 4~6 条，每条一句话）
- 功能框图

### 功能框图要求

- 只保留一张功能框图
- 功能框图应体现：
  - 上层调用方（应用层/控制算法）
  - 当前 FC 模块大框，内部按调用链体现：
    - 外部接口层（列出关键 API）
    - 内部函数层（列出核心内部函数类别）
    - 依赖接口层（列出关键 Callout）
  - 平台/硬件抽象层（MCAL / IoMcu / 项目适配层）
  - 主调用关系（请求/状态数据流）

### 推荐表现形式

- 上方或左侧为外部模块
- 中间为"当前模块"大框
- 大框内按调用链体现三层接口
- 右侧或下方为平台模块
- 从"外部模块 -> 外部接口 -> 内部函数 -> 依赖接口 -> 平台模块"计算，最大深度允许到 5 层
- 相同接口节点应合并，不重复画多个同名节点

### 禁止

- 同时渲染"功能框图"和"接口框图"两张近似图
- 只画一个 FC 方框而不体现三层调用链
- 超过三层后继续展开更细对象
- 同名接口在图中重复画多个节点

### 强化条件

以下任一成立时必须强化：

- 存在 `MainFunction`
- 存在多层 callout / 内部接口协作
- 存在复杂 fault 或状态机

## 3.5 `4. 文件列表设计`

### 目标

让开发知道会有哪些文件、各自做什么。

### 必写

- 文件名
- 必需/可选
- 职责
- 关键内容

## 3.6 `5. 单核/多核框架设计`

### 动态标题规则

- 若为单核部署，本章标题写 `## 5. 单核框架设计`
- 若为多核部署，本章标题写 `## 5. 多核框架设计`
- 不可使用模糊的 `单核/多核` 标题

### 目标

交代执行所有权、核边界和实际代码组织形态。

### 必写

- **5.1 框架设计说明**：中文完整段落，描述整体结构与实现方式
  - 单核时说明：单一执行上下文、实例直接遍历、运行时容器不分区
  - 多核时说明：每核独立数据区、Core ID 校验入口、配置 per-core 复制、同步策略
- **5.2 核模型**：每核一行，含职责、Init入口、周期任务、运行时数据
  - 单核时仅一行
- **5.3 任务模型**：Task / Core / 周期 / 调用对象 / 监控动作
- **5.4 同步点与共享对象**：
  - 单核时可填"无共享对象，所有数据在当前核内闭环"
  - 多核时列出跨核共享的 const 配置或同步点

### 强规则

- 框架设计说明必须让读者感受到实际代码组织形态，不能只写抽象标签
- 核模型必须体现各自独立的运行时数据归属
- assumptions / 已确认项目约束 对单核或多核的判断优先级高于 grounding pattern

### 禁止

- 只写空表或抽象标签
- 单核框架下出现 `CalloutGetCoreId`、核匹配、核遍历、per-core 索引等概念
- 多核框架下不写同步策略

## 3.7 `6. 接口设计`

### 目标

外部接口、内部接口、依赖接口作为整体设计，三个子章节分别承载不同调用层级，共同描述模块的完整接口体系。

### 总体规则

- 外部接口、依赖接口、关键内部控制流不应只写"功能说明"，应写出子功能拆分、执行步骤和流程图
- 流程图节点必须表达步骤，不允许直接写代码、变量更新、数组下标、寄存器名或条件表达式
- 外部 API 可以直接调用依赖接口，不必一定经过内部函数
- 调用关系表中的"类别"列支持 `内部函数` 和 `依赖接口` 两种取值

### 6.1 外部接口设计

#### 完整性规则

架构或需求中定义的所有外部接口，无论数目多少，都必须在本书中按统一格式逐一完整生成。不得因接口数目多而缩减、合并或跳过任何接口的子功能拆分、执行步骤和流程图。

#### 每个 external interface 必写

- 接口原型表（prototype / description / sync-async / reentrancy / return value / basic constraints）
- 子功能拆分表（步骤 / 子功能 / 输入 / 输出 / 关键检查约束 / 依赖对象）
- 执行步骤（有序列表）
- 调用关系表（调用对象 / 类别（内部函数或依赖接口） / 作用 / 调用时机）
- 流程图（需符合流程图规则）

#### 流程图触发条件

满足任一时必须画图：

- `Init`
- `MainFunction`
- 含 fault 分支
- 含多步检查和恢复路径
- 含复杂子功能调用链

简单 getter 不一定需要图。

#### 单核约束

单核部署时，外部接口的流程图中不得出现：
- `CalloutGetCoreId` 调用节点
- `核匹配` / `Core Match` 节点
- `核遍历` / `For Each Core` 节点
- per-core 索引或 core-id 分支

#### 调用关系表类别

调用关系表的"类别"列取值：
- `内部函数` — 本模块 static 或 Internal.h 中的函数
- `依赖接口` — Callout 或外部依赖接口（外部 API 可直接调用依赖接口，不必经过内部函数）

### 6.2 内部接口设计

#### 目标

解释模块内部职责如何归并，并按与外部接口相同的格式逐一完整展开所有内部接口。

#### 完整性规则

所有内部接口（不论复杂度高低）都必须按照与外部接口相同的格式逐一完整展开，包括接口原型表、子功能拆分、执行步骤、调用关系表和流程图。不得因"仅为简单辅助函数"而缩减、合并或跳过任何内部接口。

#### 每个 internal function 必写

- 函数原型表（prototype / description / scope / trigger point / dependency-callout）
- 依赖接口列：标注该内部函数调用了哪些依赖接口/Callout；若不调用任何依赖接口，标注 `N/A`
- 子功能拆分表（步骤 / 子功能 / 输入 / 输出 / 关键检查约束 / 依赖对象）
- 执行步骤（有序列表）
- 调用关系表（调用对象 / 类别（依赖接口或内部函数） / 作用 / 调用时机）
- 流程图（需符合流程图规则）

#### 强规则

- 必须使用规范全称
- 必须体现作用域（`static` 或 `Internal.h`）、职责、触发点、依赖接口
- 调用关系表类别列支持 `依赖接口` 和 `内部函数` 两种取值
- 仅列出内部函数而不标注其依赖接口，视为不完整
- 每个内部函数必须有流程图

#### 禁止

- 只罗列简称
- 只给总表没有逐函数完整展开
- 因函数简单而跳过子功能拆分或流程图

### 6.3 依赖接口设计

#### 目标

说明 FC 为什么依赖这些外部能力，以及如何绑定。

#### 每个 dependency 必写

- 接口原型表（prototype / description / implemented by / sync-async / reentrancy / basic constraints）
- 关联接口表（哪些外部接口或内部函数调用了此依赖接口）
- 执行步骤
- 流程图

#### 强规则

- formal dependency interface 必须全覆盖
- 关联接口表中调用方类别标注为 `外部接口` 或 `内部函数`

#### 延迟/定时 Callout 规则

当外部接口或内部流程中存在显式延迟、等待或定时需求时，必须生成对应的延迟 Callout：
- 需求或架构中指定了等待/延迟周期（如 `WaitMs`、`DelayUs`）
- 接口执行步骤中包含操作间的定时等待
- 硬件稳定时间、上电延迟或去抖等待
- 状态机迁移依赖时间流逝

## 3.8 `7. 状态机设计`

### 设计选型

状态机设计有两种可选方案：

1. **芯片硬件状态机** — 完整复刻芯片手册中定义的状态与切换规则。适用于芯片状态模型已足够覆盖驱动行为、无需额外软件状态的场景。
2. **软件驱动状态机** — 在芯片状态机之外，额外抽象一层软件驱动自身的状态（如 UNINIT / IDLE / ACTIVE / FAULT），用于管理驱动生命周期、模式切换和故障隔离。

若当前项目未积累软件驱动状态机开发经验，沿用方案 1 即可，无需强行抽象。选择方案 2 时必须在设计说明中阐述软件状态与芯片状态的映射关系。

### 目标

只在模块真的需要时强化状态机。

### 轻量模块

- 可说明"当前不构造复杂状态机"
- 需要给出弱化理由

### 复杂模块

必须体现：

- 状态定义（状态名 / 含义 / 进入条件 / 退出条件）
- 状态切换表（当前状态 / 条件函数 / 动作函数 / 下一状态 / 备注）
- 状态机主流程图

## 3.9 `8. DET设计`

### 目标

说明开发期防御性检查如何落地。

### 必写

- 检查点
- 触发条件
- 记录方式
- 返回策略
- 适用 API

## 3.10 `9. 故障处理设计`

### 目标

说明运行期异常如何检测、确认、响应、恢复，覆盖芯片故障和驱动逻辑故障两类，并定义确认策略、恢复策略、锁存语义和清除方式。

### 必写

故障处理设计必须包含以下子章节：

- **9.1 故障确认策略** — 单次确认 / 连续多次 / 累计多次，含策略说明表、适用场景、所需配置和运行参数
- **9.2 故障恢复策略** — 不可恢复 / 单次自恢复 / 连续多次自恢复，含策略说明表、适用场景、所需配置和运行参数
- **9.3 故障锁存与清除** — 锁存语义、清除方式（Init清除 / 故障清除接口 / 不可清除）、无清除接口时的约束说明
- **9.4 故障自恢复配置** — 若任一故障支持自恢复，列出所需配置宏参
- **9.5 故障项设计** — 主故障表，每故障项含：故障类型、检测条件、确认策略、确认阈值/配置、确认状态、响应动作、是否可恢复、是否可自恢复、恢复策略、恢复阈值/配置、恢复状态、触发状态跳转、锁存策略、清除方式
- **9.6 故障相关运行参数** — 确认/恢复计数器及状态变量概要

### 强规则

- 故障必须区分类型：`芯片故障`（芯片硬件触发）和 `驱动逻辑故障`（驱动内部逻辑检测）
- 确认策略必须明确（单次/连续多次/累计多次）；多次确认需给出可配置的次数阈值和运行时计数器
- 恢复策略必须明确；若支持自恢复，必须新增自恢复使能配置宏参
- 锁存故障确认后保持上报直至显式清除；若模块未设计故障清除接口，必须在清除方式列标注"Init清除"
- 故障确认和恢复的运行时计数器必须在 §10.1 运行变量中列出

### 简单模块

- 当前可轻量表达，但仍需说明故障类型、确认策略和恢复策略
- 若只有芯片故障无驱动逻辑故障，显式标注

### 禁止

- 只写"检测-确认-响应-恢复"抽象标签而不落到具体策略和计数器
- 芯片故障和驱动逻辑故障混在一起不区分类型
- 支持自恢复但未配置自恢复使能开关

## 3.11 `10. 运行参数设计`

### 目标

给出明确变量名和变量用途，并定义运行参数类型的结构化布局。

### 运行参数设计拆分原则

运行参数设计必须拆分为两个子章节，不可合并：

- `10.1 运行变量` — 运行时的变量清单，关联 `FC.c`
- `10.2 运行参数类型` — 运行时数据的结构化类型定义，关联 `FC.c` / `FC_Internal.h`

### 10.1 运行变量 必写

- 变量名
- 类别（input/status/intermediate/output/monitor/fault/retained）
- 类型
- 所属 Core
- 写方
- 读方
- 生命周期
- MemMap 放置
- NoClear 标记
- 设计依据（architecture / design-addition (Rx)）

### 10.2 运行参数类型 必写

运行参数类型定义必须包含以下子章节：

- `10.2.1 运行参数类型拆分` — 类型名、类别、所属文件、关键字段、字段类型、字段描述、关联变量、设计依据、状态。关键字段名含类型后缀，字段类型列写 C 标准类型；设计依据标注 `architecture` 或 `design-addition (Rx)`
- `10.2.2 运行参数类型设计说明` — 拆分依据、工程模式对齐情况、待确认项

### 10.2 强规则

- 至少定义一个全局运行参数类型，承载模块级状态（如 InitStatus、DET 错误记录）
- 运行参数类型拆分必须按语义边界（全局/每实例/每核/故障/监控），不得按文件大小或随意归组
- 若工程尚无运行参数类型经验：
  - 当前设计仍需提出合理类型布局
  - 整体标记 `pending-confirm`
  - 在 `10.2.2` 中标记为工程学习项
- 未定义类型对象不得进入主运行参数类型表

### 禁止

- 只写 runtime container 这类泛称
- 不写变量目的
- 只列变量不定义运行参数类型（视为运行参数设计不完整）

## 3.12 `11. 配置参数设计`

### 目标

说明配置参数设计的两个维度：配置宏参和配置类型，并校验两者是否完整覆盖架构需求。

### 配置参数设计拆分原则

配置参数设计必须拆分为两个子章节，不可合并：

- `11.1 配置宏参` — 编译期可控的开关、数量、阈值宏，关联 `FC_Cfg.h`
- `11.2 配置类型` — 配置数据的结构化类型定义与实例化，关联 `FC_CfgData.h` / `FC_Cfg.c`

### 11.1 配置宏参 必写

- 宏名
- 类别（feature / count / threshold / platform）
- 用途
- 默认值
- 来源（architecture / coding-standard / design-addition）
- 使用位置
- 状态（formal / pending-confirm）

### 11.1 强规则

- 架构设计中的每个配置参数必须有对应宏参，或显式说明为何不需要
- 详细设计过程中因编码规范引入的新增宏参（如 `FC_CFG_MAX_xxx`、`FC_CFG_xxx_ENABLED`）必须列出，来源标注 `coding-standard`
- 详细设计过程中自行增加的宏参（Source = `design-addition`）必须标注为 `design-addition (Rx)`，并关联 §14 评审项
- 宏参只用于编译期简单常量，不得将表驱动数据强行写为宏

### 11.2 配置类型 必写

配置类型定义必须包含以下子章节：

- `11.2.1 配置类型` — 类型名、类别、所属文件、关键字段、字段类型、字段描述、关联宏参、设计依据、状态。关键字段名含类型后缀，字段类型列写 C 标准类型；设计依据标注 `architecture` 或 `design-addition (Rx)`
- `11.2.2 配置类型实例化` — `Cfg.c` 中的具体配置对象定义
- `11.2.3 配置类型设计说明` — 拆分依据、工程模式对齐情况、待确认项

### 11.2 强规则

- 每个 FC 必须定义配置类型，除非该 FC 确实无任何可配置参数（需显式说明理由）
- 配置类型表中必须包含"字段描述"列，对每个关键字段说明含义、取值范围和约束
- 配置类型表中必须包含"字段类型"列，写出 C 标准类型（uint8/uint16/uint32/sint8/sint16/sint32/boolean 等）
- 关键字段名必须携带类型后缀（`_u8`/`_u16`/`_u32`/`_s8`/`_s16`/`_s32`/`_b`/`_f32` 等），与字段类型列对应
- 配置类型拆分必须按语义边界（硬件资源 / 时序阈值 / 功能使能 / 每实例 / 依赖绑定），不得按文件大小或随意归组
- 若工程尚无配置类型定义经验：
  - 当前设计仍需提出合理类型布局
  - 整体标记 `pending-confirm`
  - 在 `11.2.3` 中标记为工程学习项
- 未定义类型对象不得进入主配置类型表

### 禁止

- 只列宏参不定义配置类型（视为配置参数设计不完整）
- 将配置类型和配置宏参混在同一张表中
- 为了体现生成过程而展示 `Conf_*` 证据条目
- 正文直接展示参考模块名或外部配置对象名

## 3.14 `13. 编码起步建议`

### 目标

给开发提供具体的编码起步指引。

### 必写

- 优先实现的接口
- 优先落地的 cfg

### 推荐实现顺序

1. 建文件族与基础类型
2. 建 `Cfg.h/CfgData.h/Cfg.c`
3. 建外部接口原型与返回策略
4. 建内部函数骨架与子功能拆分

6. 接入 Callout / 依赖接口
7. 接入 DET / fault / runtime / MemMap

- 不允许的设计漂移

## 3.15 `14. 风险与待确认项`

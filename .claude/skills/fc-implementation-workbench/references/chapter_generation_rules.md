# Chapter Generation Rules

## 1. 目的

本文件定义详细设计各章节“怎么写”。

它补的是写作与展开规则，而不是字段 schema。

适用对象：

- 人工编写详细设计
- bundle 驱动的 markdown 渲染器
- 详细设计 review

## 2. 总体写作规则

### 2.1 先方案，后展开

每一章应先说明该章的设计结论或实现方案，再展开细节。

### 2.2 先结构，后叙述

优先使用：

- 表格
- 分步骤
- 关系图
- 功能框图
- 接口框图

避免大段无结构 prose。

### 2.3 先实现约束，后背景说明

详细设计优先回答：

- 开发怎么做
- 为什么这样做
- 哪些边界不能越

而不是先长篇介绍背景。

### 2.4 少写空话

出现以下表达要谨慎：

- 正常处理
- 合理管理
- 完成控制
- 进行优化
- 满足需求

这些如果不能落到具体动作或结构上，就应删掉或细化。

### 2.5 正文不展示内部生成痕迹

正文禁止直接出现：

- grounding 模块名单
- `Conf_*` 证据条目
- bundle 字段名
- 生成器 / 推断器 / schema 之类内部用语

## 3. 章节级规则

## 3.1 `1. FC概述`

### 目标

快速说明模块是谁、干什么、采取什么实现方案。

### 必写

- FC 名称
- 简洁功能介绍
- 所属层级
- 实现方案概述

### 建议

- 用 3 到 5 条描述功能范围和方案，不要只写标签

### 不要写

- 大段芯片原理背景
- 重复需求列表

## 3.2 `2. 设计输入`

### 目标

说明这份详细设计建立在哪些真实输入之上。

### 必写

- 需求文档
- 架构文档
- 芯片/平台约束
- 项目约束

### 禁止

- 展示 grounding 基线模块名
- 展示 `Conf_*` 证据条目
- 展示 bundle 内部对象名

## 3.3 待确认信息处理规则

### 规则

- 默认不单列 `待确认项` 主章节
- 仍需确认的信息应落入相关设计章节
- 配置开放边界类问题优先放入 `15. 配置宏参设计`
- 框架部署类问题优先放入 `4. 功能设计` 或 `6. 单核/多核框架设计`
- 覆盖缺口和未完全承接项可放入 `18. 架构与详细设计覆盖表` 的备注
- 不允许把实现方案写成“假设”

## 3.4 `4. 功能设计`

### 目标

说明这份详细设计的整体功能方案和架构框架思想。

### 必写

- 功能设计说明
- 功能框图
- 分层设计思想

### 功能框图要求

- 只保留一张功能框图
- 功能框图应体现：
  - 前端外部模块
  - 当前 FC 内的 external interface
  - 当前 FC 内的 internal interface
  - 当前 FC 内的 dependency interface
  - 后端依赖模块 / 平台模块
  - 主调用关系

### 推荐表现形式

- 上方或左侧为外部模块
- 中间为“当前模块”大框
- 大框内按调用链体现：
  - external interface
  - internal interface
  - dependency interface
- 右侧或下方为平台模块 / I2C / DIO / IoMcu 等资源模块
- 最多体现 3 层接口关系，再细的接口无需继续向下展开
- 相同 external / internal / dependency 接口节点应合并，不重复画多个同名节点
- 从“外部模块 -> external interface -> internal interface -> dependency interface -> 外部依赖模块”计算，最大深度允许到 5 层

### 禁止

- 同时渲染“功能框图”和“接口框图”两张近似图
- 只画一个 FC 方框而不体现 external / internal / dependency 调用链
- 只画模块内部抽象层级，而不体现外部/依赖调用关系
- 超过 external -> internal -> dependency 三层后继续展开更细对象
- 同名接口在图中重复画多个节点

### 强化条件

以下任一成立时必须强化：

- 存在 `MainFunction`
- 存在多层 callout / 内部接口协作
- 存在复杂 fault 或状态机

### 禁止

- 只重复模板标题，不写设计判断

## 3.5 `5. 文件列表设计`

### 目标

让开发知道会有哪些文件、各自做什么、依赖什么头文件。

### 必写

- 文件名
- 必需/可选
- 职责
- 关键内容
- 依赖头文件

## 3.6 `6. 单核/多核框架设计`

### 目标

交代执行所有权、架构框架思想和 core 边界。

### 何时强化

以下任一成立时必须强化：

- 存在 `CalloutGetCoreId`
- 存在 per-core runtime / cfg
- 存在跨核共享对象
- 架构明确多核部署

### 何时弱化

单核、无共享、无特殊任务模型时可以轻量写。

### 强规则

- assumptions / 已确认项目约束 对单核或多核的判断优先级高于 grounding pattern
- 不能只写空表或抽象标签

## 3.7 `7. 外部接口设计`

### 目标

这是最核心章节之一，必须让开发能据此开始实现 public API。

### 每个 external interface 必写

- 接口表
- 子功能拆分
- 执行步骤
- 参与内部接口
- 需要时流程图

### 流程图触发条件

满足任一时建议画图：

- `Init`
- `MainFunction`
- 含 fault 分支
- 含多步检查和恢复路径

简单 getter 不一定需要图。

### 强规则

- 未定义 relationship object 不得进入主接口表和主执行步骤
- 未定义对象只能进入“待修正文档关系”或覆盖/风险说明区

## 3.8 `8. 内部接口设计`

### 目标

解释模块内部职责如何归并，并按规范给出完整内部接口视图。

### 必写

- 内部接口总表
- 每个关键内部接口的小节
- 与 external/dependency 的关联关系

### 强规则

- 必须使用规范全称
- 应尽量按外部接口类似形式展开
- 必须体现类别、作用域、职责、调用方、依赖方

### 禁止

- 只罗列简称
- 只给总表没有小节

## 3.9 `9. 依赖接口与Callout设计`

### 目标

说明 FC 为什么依赖这些外部能力，以及如何绑定。

### 每个 dependency 必写

- prototype
- description
- implemented by
- 基本约束
- 关联接口

### 强规则

- formal dependency interface 必须全覆盖
- 未定义关系对象不得出现在主表“关联接口”中

## 3.10 `10. 内部控制流摘要`

### 规则

- 默认删除
- 不单独渲染
- 若确有必要，应融入 `7` 或 `8` 章，而不是形成弱价值独立章节

## 3.11 `11. 状态机设计`

### 目标

只在模块真的需要时强化状态机。

### 轻量模块

- 可说明“当前不构造复杂状态机”
- 需要给出弱化理由

### 复杂模块

必须体现：

- 软件状态机
- 芯片状态机
- 二者关系
- 状态跳转条件
- 各状态行为

## 3.12 `12. DET设计`

### 目标

说明开发期防御性检查如何落地。

### 必写

- 检查点
- 触发条件
- 记录方式
- 返回策略
- 适用 API

## 3.13 `13. 故障处理设计`

### 目标

说明运行期异常如何检测、确认、响应、恢复。

### 简单模块

- 当前可轻量表达，但仍需说明检测、响应、恢复

### 复杂模块

必须拆开：

- 故障类型
- 检测条件
- 确认条件
- 响应动作
- 恢复条件

## 3.14 `14. 运行时变量设计`

### 目标

给出明确变量名和变量用途。

### 必写

- 变量名
- 类型
- 目的
- 写方
- 读方
- 生命周期

### 禁止

- 只写 runtime container 这类泛称
- 不写变量目的

## 3.15 `15. 配置宏参设计`

### 目标

说明哪些宏参和参数需要配置。

### 必写

- 配置宏参
- 配置参数 / 配置点

### 强规则

- 配置参数应优先体现 `Cfg.c` 中真实需要配置的点
- 当已抽取到真实 `Cfg.c` 对象时，应优先按语义分组展示：
  - 顶层配置容器
  - 芯片实例配置
  - 寄存器初值配置
  - 总线映射配置
  - IO映射配置
- 正文应面向“当前模块需要配置什么”展开，不应直接展示参考模块名或外部配置对象名
- 如果当前只能提取到“需要配置哪些能力”，应明确按“配置点”表达，不能伪装成已知具体符号

### 禁止

- 单独渲染“配置表证据”
- 为了体现生成过程而展示 `Conf_*` 证据条目

## 3.16 `16. MemMap设计`

### 目标

说明代码段、常量段、运行态段如何放置。

### 必写

- section
- 内容
- 起止宏
- 所属文件

## 3.17 `17. 代码编写限制要求`

### 目标

给出 coding 时必须遵守的边界和限制。

### 必写

- 不允许的设计漂移
- 接口一致性要求
- 配置边界要求
- 依赖接口使用限制

## 3.18 `18. 架构与详细设计覆盖表`

### 目标

体现 architecture freeze 如何被 detailed design 承接。

### 必写

- 架构对象
- 架构分类
- DD落位章节
- DD对象名
- 覆盖状态
- 备注

## 3.19 `19. 风险与待确认项`

### 规则

- 默认删除
- 若项目确有需要，可由 `3. 待确认项` 承接

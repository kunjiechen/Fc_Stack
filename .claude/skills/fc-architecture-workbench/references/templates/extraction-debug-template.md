提取完成后自检：
- 是否每条需求都检查了“动作”和“属性”是否同时存在
- 是否区分了“运行方式”和“前置条件”
- 是否显式提取了“数据有效性/时间戳/有效标志/刷新周期”这类信息

- 是否明确了数据是“谁写入、谁缓存、谁读取、谁上报”

判定前先增加一句检查：
- 这是“运行期反复发生的人机/上层交互动作”，还是“启动时一次确定的环境配置”
- 如果是后者，优先不要生成接口，改为落入配置参数或初始化配置结构
- 如果是前者，优先尝试匹配 `demo` 中已有的语义化接口风格，而不是先生成泛化的 `GetInput` 或 `SetOutput`

接口分类扫描时，不允许跳过以下类别：
- 初始化接口
- 周期任务接口
- 外部调用接口
- 内部模块接口
- 回调/通知接口
- 中断相关接口
- 数据读接口
- 数据写接口
- 配置访问接口
- 标定访问接口
- 诊断/错误处理接口
- 状态查询接口
- OS/调度接口
- MCAL/底层依赖接口
- 内存段相关宏或集成可见项

## 3. 配置宏参判定表

配置宏参表统一体现两类内容：
- 基础配置
- 功能相关配置

说明：
- 不同项目的配置宏参值可以不同，例如喂狗时间在 A 项目为 `100ms`，B 项目为 `200ms`
- 常规寄存器配置通常在 `Cfg.c` 中配置，架构阶段只识别其“属于配置宏参范围”，不强制限制具体组织写法
- 寄存器相关配置不视为运行期间可随意修改的量
- 除非需求明确指出某功能需要标定，否则默认无标定项

## 6. 接口遗漏检查

请逐项检查：

- 是否每个模块都有 `Init` 接口或明确说明不需要
- 是否每个周期任务都有 `MainFunction` / Runnable / Task 承载
- 是否每个输入信号都有接收或读取接口
- 是否每个输出信号都有发送、写入或控制接口
- 是否每个跨模块数据都有 `Get/Set` 或共享数据策略
- 是否每个错误场景都有诊断、故障读取或上报路径
- 是否每个配置项都有宏、配置表或结构承载
- 是否每个标定项都有变量声明和内存段归属
- 是否每个外设交互都有底层调用接口、标准绑定或 callout 承载

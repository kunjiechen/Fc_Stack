# AURIX2G 架构设计细节学习与后续设计指导

## 1. 文档目的

本文件不是对 `AURIX2G` 工程功能的介绍，而是专门提炼该工程以及现有参考文档中，能够支撑后续“新驱动 FC 架构设计”的细节性方法。

目标是回答两个问题：

1. 后续新驱动在做架构定义时，应该具体怎么设计。
2. 当前留下来的文档资产，是否足以支撑后续代码开发。

## 2. 适用范围

本文件用于指导后续新驱动或新 FC 的架构定义，重点覆盖：

- 接口设计
- 接口命名
- 传参与参数命名
- 配置参数抽取与尺度控制
- 多核与单核架构设计
- 全局变量与运行态设计
- 标定量设计
- 内存段宏设计
- 文件划分与包含关系
- 依赖接口与 callout 设计

## 4. 这套资产是否足以支撑后续代码开发

结论先说：

- 能支撑后续新驱动的架构设计。
- 能支撑代码骨架设计。
- 能支撑文件划分、接口定义、配置抽取、运行态建模、MemMap 规划。
- 不能单独支撑最终业务实现细节和项目落地配置。

### 4.1 已足够支撑的内容

- FC 文件族如何划分
- 外部接口如何命名
- 接口应采用什么返回值形式
- 参数命名与指针输出风格
- 哪些内容属于 `Cfg`、哪些属于运行态、哪些属于标定
- 多核/多实例如何组织
- Callout 应如何定义
- `MainFunction` 是否需要
- 内存段宏应如何分
- 文件包含关系如何控制

### 4.2 仍需项目补充的内容

- 具体芯片信号定义与寄存器细节
- Core / Chip / Channel / Signal 的真实映射
- OS 周期与任务绑定
- 故障阈值、恢复阈值、时序窗口的项目值
- 标定流程是否存在
- 项目是否需要 DEM / NvM / WdgIf 等标准依赖

因此，这套文档资产适合作为“平台级架构方法库”，而不是“项目最终配置输入”。

## 5. 后续新驱动设计的总流程

建议后续每个新驱动都按以下顺序做架构设计：

1. 先判定模块所在层级
2. 第一轮提取显式接口
3. 第二轮补全隐式接口
4. 第三轮做项目风格与规范对照
5. 第四轮做遗漏与冲突检查
6. 再确定运行模型
7. 再做配置与运行态分类
8. 再设计文件族
9. 再设计依赖接口与 callout
10. 最后设计 MemMap 和包含关系

不要反过来从 `.c` 实现开始倒推架构。

### 5.1 为什么接口最容易漏

接口最容易遗漏的典型场景包括：

- 需求只写行为，不写接口名
- 接口隐藏在数据流里
- 中断、回调、通知接口
- 初始化、反初始化、配置初始化接口
- 配置访问接口
- 标定访问接口
- 诊断与错误处理接口
- 跨层数据同步接口

因此，后续架构设计不能只做“一轮接口提取”。

### 5.2 推荐的防漏机制

后续每次做接口提取，都建议固定执行：

1. 显式接口提取
2. 隐式接口补全
3. 规则与项目风格对照
4. 需求正向追踪
5. 接口反向追踪
6. 遗漏风险检查
7. 置信度标记

输出中应至少包含：

- 接口清单
- 接口分类
- 来源需求ID
- 推导依据
- 置信度
- 是否需要人工确认
- 接口覆盖率表
- 遗漏风险清单

## 6. 接口设计指导

### 6.1 先定义“接口语义”，不要先定义函数名

设计接口前先回答：

- 这是初始化动作，还是运行期控制动作
- 这是即时读取，还是周期缓存读取
- 这是资源接口、信号接口、器件接口，还是系统接口
- 这是提交请求，还是返回状态

只有在这些问题清楚后，接口名和参数才会自然收敛。

### 6.1.1 接口分类扫描必须固定化

后续做接口提取时，建议强制按下列类别逐项扫描，不允许跳过分类：

- 初始化接口
- 周期任务接口
- 外部调用接口
- 内部模块接口
- 回调/通知接口
- 中断相关接口
- 数据读接口
- 数据写接口
- 配置访问接口
- 标定访问接口
- 诊断/错误处理接口
- 状态查询接口
- OS/调度接口
- MCAL/底层驱动接口
- 内存段相关宏或集成可见项

这样做的目的不是让这些接口都出现，而是防止“没扫到这一类”。

### 6.2 对外接口的标准骨架

后续新驱动默认先从以下骨架出发：

- `FC_Init(void)`
- `FC_MainFunction(void)`，仅在确有周期逻辑时保留
- `FC_Set...OutSig(...)`
- `FC_Get...InSig(...)`
- `FC_Get...Diag(...)`
- `FC_Get...FaultSig(...)`

### 6.3 哪些场景必须考虑 `MainFunction`

若存在以下任一内容，优先定义 `MainFunction`：

- 周期采样
- 状态机推进
- 故障诊断
- 自动恢复
- 去抖
- 计数器推进
- 输出请求延后生效
- 看门狗或后台维护

若模块本质是一次性控制或同步读写工具，则可以不设计 `MainFunction`。

### 6.4 接口返回值设计

推荐规则：

- `Init`、`MainFunction` 默认 `void`
- 其他对外接口默认 `Std_ReturnType`
- 业务值通过输出指针返回

原因：

- 便于做参数合法性、初始化状态、核归属检查
- 保持与现有工程风格一致

不建议默认使用：

- 直接返回业务值
- 直接暴露全局变量供外部读取

## 7. 接口命名指导

### 7.1 总体命名风格

后续新驱动的接口命名应优先继承现有工程习惯：

- `Init`
- `MainFunction`
- `SetDevModeOutSig`
- `SetDrvOutSig`
- `SetHbOutSig`
- `GetDevModeInSig`
- `GetCurSig`
- `GetDevFaultSig`
- `Get...Diag`

原则：

- 接口名应体现“业务语义”
- 不应体现底层技术细节
- 不应只剩抽象的 `Read` / `Write` / `Ctrl`

### 7.2 推荐命名策略

资源类接口：

- `GetAdcSigAdcRaw`
- `GetDioSigLvlIn`
- `SetDioSigLvlOut`

器件类接口：

- `SetDevModeOutSig`
- `SetDrvOutSig`
- `GetCurSig`
- `GetDevFaultSig`

系统类接口：

- `GetState`
- `RecordState`
- `PerformReset`

### 7.3 不推荐的命名

- `GetInput`
- `SetOutput`
- `ReadData`
- `WriteCmd`
- `DoAction`

这些名字过于泛化，后续无法稳定扩展。

## 8. 传参与参数命名指导

### 8.1 外部接口参数设计原则

优先减少外部参数维度。

多核、多芯片、多通道场景中，对外优先只暴露：

- `Id_u16`

不要轻易对外暴露：

- `CoreId`
- `ChipId`
- `ChannelId`
- `SignalId`

这些维度应尽量在内部通过映射表解析。

### 8.2 参数命名风格

建议保持当前工程风格：

- 输入参数：
  - `Id_u16`
  - `Mode_u8`
  - `Duty_u32`
  - `Dir_te`
- 输出指针：
  - `Cur_pf32`
  - `Fault_pu32`
  - `Lvl_pb`

规则：

- 参数语义名在前
- 类型后缀在后
- 指针显式写出 `p`

### 8.3 传参尺度控制

要避免两种极端：

- 参数过少，语义不清
- 参数过多，把内部结构泄露给外部

推荐做法：

- 外部接口只传“业务所需最小集合”
- 内部复杂组合进入运行态或配置表

例如：

- 对外传 `Id + Mode`
- 不对外传 `CoreId + ChipIdx + DioCh + PwmCh + DelayCfg`

### 8.4 参数设计也要做置信度判断

当需求没有明确给出参数形态时，建议在架构输出中标记：

- 参数是需求明确给出
- 参数是按项目风格推导
- 参数是低置信度推断

低置信度参数组合不要直接进入代码实现，应先进入待确认项。

## 9. 配置参数抽取与尺度控制

这是后续架构设计里最关键的点之一。

### 9.1 配置抽取的四分类

后续所有需求项都应优先分类为：

- 外部接口
- 配置参数
- 标定参数
- 运行态数据

### 9.2 `Cfg.h` 适合承载什么

适合放入 `Cfg.h` 的内容：

- 功能开关
- 基础数量
- 模式选择
- 实现选择
- 编译期开关
- 核使能
- 每核实例数
- 对外 `ID` 宏

### 9.3 `Cfg.c / CfgData.h` 适合承载什么

适合放入表驱动配置的内容：

- 硬件资源绑定
- `Id -> Core/Chip/Channel/Signal` 映射
- 芯片配置容器
- 时序参数表
- 诊断阈值表
- 恢复阈值表
- 物理换算参数

### 9.4 不要把所有东西都做成宏

不推荐：

- 每个阈值都在 `Cfg.h` 平铺成大量宏
- 每个寄存器字段都直接暴露为宏

推荐：

- 基础选择项进 `Cfg.h`
- 具体项目数据进 `Cfg.c / CfgData.h`

### 9.5 配置尺度判断方法

如果某项：

- 项目启动前就确定
- 运行时不变
- 主要用于实例化和映射

则优先作为配置。

如果某项：

- 每周期变化
- 需要缓存
- 属于结果、状态、计数器、请求

则优先作为运行态。

## 10. 多核与单核代码架构设计

### 10.1 单核设计原则

单核场景下：

- 外部接口仍可保持 `Id`
- 配置表可简化
- 运行态可仅一个实例或一组数组
- 不要为了单核强行展开过度复杂结构

### 10.2 多核设计原则

多核场景下应优先设计：

- `CORE_NUM`
- `CORE0~CORE5` 使能
- 每核独立运行态
- 每核独立配置指针
- 全局 `RunTimeType rtCont[]`

### 10.3 多核外部接口设计原则

优先：

- 外部传统一 `Id`
- 内部查 `cfgSigMapping`
- 当前核通过 `GetCoreId` 校验合法性

不推荐：

- 外部接口直接带 `CoreId`
- 各核写多套完全独立接口

### 10.4 多核代码结构原则

推荐结构：

- `Cfg` 中表达核使能与每核实例数
- `C` 中按核定义缓冲
- `Types.h` 中统一 `RunTimeType`
- `Callout` 中提供 `GetCoreId`

## 11. 全局变量与运行态设计

### 11.1 对外不要以全局变量作为接口

这是必须坚持的规则。

对外接口应以函数为主，不应让外部直接访问运行态全局变量。

### 11.2 模块内部应显式设计运行态

推荐至少考虑以下运行态对象：

- 初始化状态
- 接口检查状态
- 状态机当前状态
- 输入请求缓存
- 输出结果缓存
- 故障位图
- 故障计数
- 恢复计数
- 周期计数 / 去抖计数

### 11.3 运行态应尽量结构化

优先：

- `IfChkType`
- `CtrlDatType`
- `DiagDatType`
- `MultiChipType`
- `RunTimeType`

不推荐：

- 大量散乱的独立静态变量

### 11.4 全局变量命名

若必须有模块内部全局变量，应遵守统一命名和类别标识：

- `_l...` 文件内变量
- `_v...` 接口可见变量
- `_k...` 标定量

## 12. 标定量设计

### 12.1 默认不要滥用标定量

在 BSW / 驱动 FC 中，大多数参数更适合作为配置，而不是标定。

只有满足以下条件，才建议设计标定量：

- 后续确有调参需求
- 存在标定流程或标定工具
- 值在项目后期可能持续调整
- 它不是简单的资源绑定或固定映射

### 12.2 适合做标定量的典型内容

- 算法阈值
- 滤波系数
- 控制增益
- 上下限判定值

### 12.3 不适合做标定量的典型内容

- DIO/PWM/ADC 通道 ID
- Core/Chip/Signal 映射
- 是否开启某功能
- 固定的寄存器默认配置

### 12.4 标定量落点

推荐：

- 定义在 `FC_Cali.c`
- 声明在 `FC_CfgData.h`

命名应按单个标定量展开，不要做成“标定配置容器表”。

## 13. 内存段宏设计

### 13.1 一个 FC 至少应考虑哪些内存段

后续新 FC 默认至少规划以下内存段：

- 代码段
- 配置常量段
- 运行态变量段
- 可选标定段

如果模块存在多核隔离要求，可进一步细分为：

- `CORE0~CORE5` 数据段
- `GLOBAL` 常量段
- `CORE0~CORE5` 常量段（当 static const 或配置常量按核归属/复制时）
- `CALI` 常量段

### 13.2 推荐最小段集合

简单 FC 推荐最小集合：

- `CODE_START / CODE_STOP`
- `CONST_START / CONST_STOP`
- `VAR_START / VAR_STOP`

复杂多核 FC 推荐扩展集合：

- `CLEAR_FAR_DATA_ALIGN4_CORE0_START/STOP`
- `...CORE1...`
- `CONST_FAR_DATA_ALIGN4_GLOBAL_START/STOP`
- `CONST_FAR_DATA_ALIGN4_CORE0_START/STOP`
- `...CORE1...`
- `CONST_FAR_DATA_ALIGN4_CALI_START/STOP`

### 13.3 何时增加 `NO_CLEAR` 段

若模块涉及：

- 跨复位信息保留
- reset 诊断记录
- 启动原因保留

则应考虑 `NO_CLEAR` 段，例如 `Gp_RstM`。

### 13.4 内存段设计原则

- 段设计要服务于数据生命周期
- 不要只为形式而细分段
- 多核缓冲、全局配置、标定、NoClear 要分开考虑
- 多核 static const 或按核配置表不能默认合并到 `GLOBAL`，应补充 `CONST_FAR_DATA_ALIGN4_COREx_START/STOP`

## 14. 文件划分与包含关系

### 14.1 默认文件族

新驱动默认先按以下文件族规划：

- `FC.h`
- `FC.c`
- `FC_Types.h`
- `FC_Cfg.h`
- `FC_Cfg.c`
- `FC_CfgData.h`
- `FC_MemMap.h`

按需增加：

- `FC_Callout.h`
- `FC_Callout.c`
- `FC_Cali.c`
- `FC_Reg.h`
- `FC_Internal.h`

规则补充：

- 涉及 SPI/I2C/register 外设通信时，应增加 `FC_Reg.h`，用于寄存器地址、位定义、命令字和协议帧常量。
- 存在 Callout 依赖时，文件列表应同时包含 `FC_Callout.h` 和 `FC_Callout.c`。
- `_MemMap.h` 应作为所有 section-managed FC 文件的段边界包含关系体现。

### 14.2 推荐包含关系

推荐主链路：

- `FC.h` 包含 `FC_CfgData.h`
- `FC_CfgData.h` 包含 `FC_Types.h`
- `FC_Types.h` 包含 `FC_Cfg.h`
- `FC_Reg.h` 包含 `Std_Types.h`
- 涉及寄存器配置时，`FC_Cfg.h` 包含 `FC_Reg.h`

这样可以形成：

- `Cfg.h` 提供宏和基础配置
- `Types.h` 基于 `Cfg.h` 定义类型
- `CfgData.h` 基于 `Types.h` 声明配置对象
- `FC.h` 再对外暴露接口

### 14.3 不推荐的包含方式

- `FC.h` 直接包含大量底层平台头文件
- `Types.h` 直接包含业务无关的实现源依赖
- `Cfg.h` 包含复杂业务头文件

### 14.4 包含关系控制原则

- 上层头文件依赖下层抽象，不反向依赖
- `Types.h` 保持相对纯净
- 平台细节尽量留在 `Callout.c`

## 15. Callout 与依赖接口设计

### 15.1 何时用标准 FC，何时用 Callout

优先级建议：

1. 先复用标准 FC，如 `IoMcu`、`IoSigSrv`
2. 无法统一时再用 `Callout`
3. 简单能力才考虑宏替换

### 15.2 Callout 参数设计原则

Callout 参数应反映 FC 的真实需求，而不是底层平台实现细节。

Callout 原型规则：

- 不使用数组形参写法，例如 `uint8 TxData_au8[]`。
- 使用指针形参，例如 `uint16* TxData_pu16`、`uint16* RxData_pu16`、`uint8* Data_pu8`。
- 传输长度/帧数默认使用 `uint16 Size_u16`。
- 16bit SPI 帧协议使用 `uint16*` 数据指针，避免调用处反复强转。

例如推荐：

- `Set logical level`
- `Get adc raw`
- `Set pwm period and duty`

不推荐：

- 直接把 AUTOSAR sequence、job、channel group 等细节抬到 FC 外部

### 15.3 推荐宏化的依赖

以下简单依赖可优先考虑宏：

- `ENTER_CRITICAL`
- `EXIT_CRITICAL`

## 16. 后续设计时的判断清单

每设计一个新驱动，建议至少回答以下问题：

1. 它属于 `IoMcu`、`IoSigSrv`、`IoExtDev`、`Cdd`、`BswSys` 还是其他层。
2. 它对外暴露的是资源能力、信号能力、器件能力还是系统能力。
3. 它是否需要 `MainFunction`。
4. 它的运行态是否需要状态机、故障计数、恢复计数。
5. 它是否需要多核/多实例映射。
6. 哪些内容应该进入 `Cfg.h`，哪些进入 `Cfg.c/CfgData.h`。
7. 是否真的存在标定量。
8. 是否需要 `NoClear` 段。
9. 是否需要 `Callout`。
10. 文件族是否完整。

## 17. 接口遗漏检查建议

后续每次提取接口时，建议固定输出一段“接口遗漏检查”：

- 是否每个模块都有 `Init` 接口或明确不需要
- 是否每个周期任务都有 `MainFunction` / Runnable / Task 承载
- 是否每个输入信号都有接收或读取接口
- 是否每个输出信号都有发送、写入或控制接口
- 是否每个跨模块数据都有 `Get/Set` 或共享数据策略
- 是否每个错误场景都有诊断、故障读取或上报路径
- 是否每个配置项都有宏、配置表或结构承载
- 是否每个标定项都有变量声明和内存段归属
- 是否每个外设交互都有底层调用接口、标准绑定或 callout 承载

如果这些检查项不输出，接口遗漏风险会显著升高。

## 18. 能否支撑后续代码开发的最终判断

最终判断是：

- 可以支撑后续架构设计。
- 可以支撑后续代码骨架开发。

- 不能替代具体项目需求。

- 不能替代寄存器手册。

因此，后续最理想的使用方式是：

- 先用本文件做架构设计
- 再结合项目需求补齐配置与实现

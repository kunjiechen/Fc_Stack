# Gp_TLE92104 FC Architecture Summary

This summary replaces the retained demo source/config files for future FC architecture work. Use it as style evidence, not as a mandatory implementation template.

## Positioning

- Layer: IoExtDev external device layer
- Role: Control TLE92104-like half-bridge driver chips via SPI, DIO and PWM dependencies, with internal chip state and fault record handling.
- Best-fit scenario: Complex SPI external chip driver; good reference for chip init, SPI register access, mode control, HB output, fault/status cache, and periodic background handling.

## Configuration and Calibration Guidance

- DET/MCAL switches are formal only when the project needs compile-time behavior selection.
- Per-core enable and chip count are count/size macros.
- Register addresses/defaults belong in register/config headers, not in external APIs.

## Runtime-State Guidance

- Per-chip runtime stores register shadows, target/current mode, fault record, SPI buffers, HB output request and diagnostic state.
- MainFunction drives chip init, mode control, SPI communication, fault record and status update.

## MemMap Guidance

- CODE for APIs, SPI helpers, mode control, chip init.
- CONST for chip config/register defaults.
- CLEAR_FAR_DATA per-core/chip runtime containers.

## Reusable Architecture Lessons

- Complex chip drivers need dependency interfaces for SPI, DIO, PWM, delay and core ID.
- Do not leak SPI register details into external FC APIs.
- Use internal register abstraction and state machine for initialization/mode/fault work.

## Use and Non-Use Rules

- Use this summary to select architecture patterns, not to copy all interfaces or macros blindly.
- Re-run configuration macro necessity checks before promoting any macro to formal output.
- Re-run dependency necessity checks before promoting any callout to formal output.
- Prefer user requirements and current project constraints over this historical sample summary.

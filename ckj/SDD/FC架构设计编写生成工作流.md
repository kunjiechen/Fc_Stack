# FC架构设计编写生成工作流

## 1 目的

本文档定义 FC（Function Component）软件架构设计规范（SDD）的生成工作流，用于指导从已完成的软件需求规范、架构编写规范、模板、文档标准和系统流程约束中生成完整、可实施、可追溯的软件架构设计文档。

本工作流适用于 FcStack 中 MCAL、BSW、IoExtDrv、CDD、ASW 等 FC 模块的软件架构设计、评审和进入 SDS 阶段前的质量门禁。

## 2 输入范围

FC 架构设计编写生成应至少使用以下输入：

| 输入类别 | 推荐位置 | 用途 |
| --- | --- | --- |
| SRS 需求规范 | `Output/[FC_SHORT_NAME]/Doc/SRS/` | 提供模块职责、接口、状态、配置、错误、安全、时序、资源和验证策略输入 |
| SDD 编写规范与模板 | `Standard/RuleAndTemplate/SDD/` | 约束 SDD 文档结构、架构设计内容、编号、评审和模板格式 |
| 文档类标准规范 | `Standard/Conversion/Doc/` | 约束需求质量、流程图表达、文档质量和评审规则 |
| 系统流程与 V 模型约束 | `System/` | 约束阶段出口、追溯、评审、验证、变更和下游输入要求 |

若 SRS 或系统输入不足以支撑确定性架构设计，应登记开放项并回写 SRS 问题清单，不得在 SDD 中静默补齐未定义的软件行为。

## 3 输出范围

FC 架构设计阶段建议输出以下文件：

| 输出物 | 文件名建议 | 说明 |
| --- | --- | --- |
| 架构输入索引 | `Architecture_Input_Index_[FC_SHORT_NAME].md` | 记录 SRS、标准、系统流程和其他设计输入的适用章节、版本和用途 |
| SRS 到 SDD 覆盖矩阵 | `Trace_SRS_SDD_[FC_SHORT_NAME].md` | 记录每条 SRS 如何被 SDD 设计项覆盖、N/A 或保持开放 |
| 需求-架构设计追溯矩阵 | `需求-架构设计追溯矩阵_[FC_SHORT_NAME].html` | HTML 格式可视化追溯矩阵，存放在 `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/`，支持交互浏览和筛选 |
| 架构决策记录 | `Architecture_Decision_[FC_SHORT_NAME].md` | 记录关键架构判断、备选方案、选择理由和影响范围 |
| 软件架构设计规范 | `SDD_[FC_SHORT_NAME].md` | 正式 FC 软件架构设计规范 |
| 接口规范 | `InterfaceSpec_[FC_SHORT_NAME].md` | API、参数、返回值、同步/异步、可重入性和调用约束；可独立成文或作为 SDD 章节 |
| 时序规格 | `TimingSpec_[FC_SHORT_NAME].md` | 周期、响应时间、同步/异步、阻塞边界和调度模型；可独立成文或作为 SDD 章节 |
| 状态机设计 | `StateMachine_[FC_SHORT_NAME].md` | 状态集合、事件、转移、保护条件和异常路径；可独立成文或作为 SDD 章节 |
| 安全机制设计 | `SafetyDesign_[FC_SHORT_NAME].md` | 安全机制、故障检测、响应、降级、安全状态和验证入口；可独立成文或作为 SDD 章节 |
| SDD 评审记录 | `Review_SDD_[FC_SHORT_NAME].md` | 记录门禁检查、问题、结论和遗留风险 |
| 实际操作步骤 | `Operation_Steps_SDD_[FC_SHORT_NAME].md` | 记录本次 SDD 生成的实际执行步骤、输入文件、关键判断、问题处理和输出文件路径 |
| SDD CHECK 清单 | `CHECK_SDD_[FC_SHORT_NAME].md` | 汇总 Gate 1 至 Gate 7 的检查结果、问题、责任人、关闭状态和最终发布结论 |

上述输出物应存放在与架构设计文档 `SDD_[FC_SHORT_NAME].md` 相同的输出路径下。若项目约定输出目录为 `Output/[FC_SHORT_NAME]/Doc/SDD/` 或其他路径，则实际操作步骤和 SDD CHECK 清单必须与 SDD 文档同目录归档，不得散落在临时目录或工具目录中。

## 4 工作流总览

```text
架构输入收集
    ↓
架构输入索引
    ↓
SRS 输入充分性确认
    ↓
架构职责与边界设计
    ↓
接口、数据流、状态机、配置、依赖设计
    ↓
时序、资源、诊断、安全、多核与集成设计
    ↓
SRS 到 SDD 追溯建立
    ↓
质量门禁检查
    ↓
问题修正与开放项闭环
    ↓
生成实际操作步骤与 CHECK 清单
    ↓
SDD 评审与基线
    ↓
进入 SDS 阶段
```

## 5 工作步骤

### 5.1 步骤一：建立架构输入索引

目标：明确 SDD 生成所依赖的全部输入资料，确保每项输入都有明确用途和可追溯位置。

架构输入索引应至少包含：

| 字段 | 说明 |
| --- | --- |
| 输入ID | 如 `AIN-[FC_SHORT_NAME]-0001` |
| 文件名称 | 输入文件名称，不写绝对路径 |
| 输入类型 | SRS、IRS、安全输入、标准规范、系统流程、平台约束等 |
| 章节/位置 | 可追溯到具体章节、标题、页码或条目 ID |
| 版本/日期 | 若输入资料提供版本，应记录 |
| 是否适用 | 是/否/部分适用/待确认 |
| 适用说明 | 说明该输入对 SDD 的作用 |
| 预期设计类别 | ARCH/FILE/INTF/DATA/STATE/CFG/DEP/TIM/RES/DIAG/SAFE/CORE/MEM/VER |

完成标准：

- `Output/[FC_SHORT_NAME]/Doc/SRS/` 中与当前 FC 相关的 SRS 已登记。
- `Standard/RuleAndTemplate/SDD/` 中 SDD 编写规范和模板已登记。
- `Standard/Conversion/Doc/` 中适用的文档规范、流程图规范和质量标准已登记。
- `System/` 中 V 模型流程、阶段出口和追溯约束已登记。
- 不适用输入已说明 N/A 原因。

### 5.2 步骤二：确认 SRS 输入充分性

目标：确认 SRS 足以支撑 SDD 设计，避免架构阶段自行定义未需求化行为。

应检查 SRS 是否至少明确：

| 输入项 | SDD 使用方式 |
| --- | --- |
| 模块职责 | 定义模块边界、职责和非职责 |
| 对外接口 | 固化 API 能力、参数、返回值和调用约束 |
| 模式/状态 | 建立状态集合、状态语义和状态转移 |
| 配置项 | 建立配置项、配置结构和一致性规则 |
| 硬件约束 | 设计下层依赖、Callout、寄存器抽象或集成约束 |
| 错误类别 | 设计 DET、DEM、内部错误、返回值和失败后置条件 |
| 多实例 | 设计实例 ID、配置映射和运行时数据隔离 |
| 多核/重入 | 设计核访问权限、同步策略和接口可重入性 |
| 安全边界 | 设计安全机制、故障响应、降级路径和安全状态 |
| 时序/资源 | 设计调度模型、响应时间、资源预算和验证方式 |
| 验证策略 | 建立架构验证、IT/ST 输入和追溯入口 |
| 通用化边界 | 区分 FC 通用架构、配置裁剪能力和集成环境约束 |

处理规则：

- SRS 输入明确时，进入架构设计。
- SRS 输入缺失但不影响架构主线时，登记开放项并标注不阻塞原因。
- SRS 输入缺失且影响接口、状态、安全、配置、错误处理或验证时，不得继续固化设计，应回写 SRS 问题或需求变更。

### 5.3 步骤三：设计架构职责与边界

目标：明确 FC 位于软件架构中的位置、负责什么、不负责什么，以及可复用边界。

应生成以下内容：

| 内容 | 要求 |
| --- | --- |
| 模块架构摘要 | 模块名称、简称、层级、安全等级、运行方式、实例模型、配置方式和主要依赖 |
| 模块位置图 | 表达上层调用者、FC、下层依赖和硬件/外设关系 |
| 模块职责表 | 每项职责有 SDD ID、职责描述、来源 SRS 和下游 SDS 入口 |
| 非职责边界 | 明确模块不负责的能力、原因和责任归属 |
| 支持/非支持能力 | 区分芯片/平台能力、本模块支持能力和处理方式 |
| 通用化与适配边界 | 明确哪些差异通过配置、Callout、依赖抽象或集成约束承载 |

设计规则：

- SDD 只细化 SRS 已定义的软件行为和约束。
- 不得把某项目的目录、任务名、通道号、板级接法或单一 OS 策略写成 FC 固有架构。
- 与具体集成环境相关的差异应优先通过配置、Callout 或外部集成约束承载。

### 5.4 步骤四：设计接口、数据流、状态机、配置和依赖

目标：形成足以指导 SDS 和编码的高层结构设计。

#### 5.4.1 接口设计

接口设计应至少包含：

| 属性 | 要求 |
| --- | --- |
| API 名称 | 符合命名规范，在全局命名空间唯一 |
| SDD ID | 符合 `SDD-[FC_SHORT_NAME]-INTF-[NNNN]` |
| 来源需求 | 明确 SRS ID 或批准的设计约束来源 |
| 同步/异步 | 明确调用返回时是否完成动作 |
| 可重入性 | 明确 Reentrant/Non-Reentrant 及多核约束 |
| 参数 | in/inout/out、类型、范围、空指针行为 |
| 返回值 | 明确 E_OK/E_NOT_OK 或自定义状态语义 |
| 前置/后置条件 | 明确初始化、配置、状态、成功和失败后的影响 |
| 错误处理 | 明确 DET/DEM/内部错误/返回值边界 |

#### 5.4.2 数据流设计

数据流设计应至少包含：

- 输入从上层接口到内部运行时数据的流转路径。
- 输出从下层依赖、状态机或运行时状态到上层接口的流转路径。
- 配置数据、标定数据、运行时数据和诊断状态的作用域。
- 多实例、多核共享数据的保护策略。
- 软件请求状态、软件记录状态、硬件确认状态和不可确认状态的区分。

#### 5.4.3 状态机与模式设计

状态机与模式设计应至少包含：

- 状态/模式集合。
- 初始状态、进入条件、退出条件和状态语义。
- 状态转移表和状态机图。
- 非支持模式和非法转换处理。
- 安全状态、故障状态、降级和恢复条件。

#### 5.4.4 配置设计

配置设计应至少包含：

- 配置项清单。
- 配置结构字段、类型、范围和必填性。
- 配置一致性规则。
- 配置错误检测时机和失败行为。
- 配置与实例数、通道数、资源和启用能力的关系。

#### 5.4.5 依赖与 Callout 设计

依赖与 Callout 设计应至少包含：

- 依赖对象、依赖类型、调用方向、用途和失败反馈。
- Callout 输入、输出、返回值、功能语义和集成要求。
- 下层接口无返回值时的不可确认状态或固定成功理由。
- 替代、Stub 或集成适配策略。

### 5.5 步骤五：设计时序、资源、诊断、安全、多核与集成

目标：补齐架构阶段必须明确的非功能、集成和验证相关设计。

| 设计域 | 必须明确内容 |
| --- | --- |
| 时序与调度 | 周期、触发、执行上下文、同步/异步、超时、忙状态、有界等待 |
| 资源 | ROM、RAM、Stack、CPU Load 的预算、估算方式或集成阶段测量计划 |
| 诊断与错误处理 | 参数错误、配置错误、状态错误、硬件错误、DET/DEM/内部错误边界 |
| 安全机制 | 安全需求来源、ASIL、检测对象、故障响应、安全状态、恢复策略和验证方式 |
| 多实例 | Instance ID 范围、配置映射、运行时数据隔离和无效实例处理 |
| 多核与重入 | 支持核、核访问权限、共享数据、同步策略、非法核处理和接口可重入性 |
| Memory Map | Code/Const/Var 段宏、配置常量、运行时变量和 MemMap 文件边界 |
| 集成设计 | 构建系统、Include 路径、配置文件、Callout、OS/RTE/SchM/MCAL 集成点 |

设计规则：

- 不得设计无限等待。
- 临界区必须短小并明确保护对象。
- 资源没有可靠数值时，应写明评估方法和验证阶段，不得编造数值。
- 安全机制必须有安全需求、安全分析或评审来源。
- QM 模块不得在无安全来源时宣称 ASIL 安全机制。

### 5.6 步骤六：建立 SRS 到 SDD 追溯

目标：证明每条有效 SRS 均被 SDD 覆盖、合理 N/A 或登记开放项。

追溯矩阵应至少包含：

| 字段 | 说明 |
| --- | --- |
| SRS ID | 上游需求 ID |
| SRS 主题 | 需求标题或摘要 |
| SDD ID | 覆盖该需求的架构设计项 |
| 设计项 | 架构项、接口、状态机、配置、依赖、安全机制等 |
| 下游 SDS/接口/测试入口 | 后续详细设计、接口规范、IT/ST 输入 |
| 状态 | Covered/Open/N/A/Changed/Deprecated |
| 说明 | N/A、Open 或变更原因 |

追溯规则：

- 每条 SRS 至少被一个 SDD 项覆盖或说明 N/A 理由。
- 一个 SDD 项可覆盖多个 SRS，但不得导致职责混乱。
- SDD 新增的架构约束必须能追溯到平台规范、系统流程、标准或批准的架构决策。
- 安全相关 SRS 必须追溯到安全机制设计和验证策略。

HTML 追溯矩阵生成与检查：

- 追溯矩阵完成后，应生成 HTML 格式文件 `需求-架构设计追溯矩阵_[FC_SHORT_NAME].html`，存放在 `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/`。
- HTML 追溯矩阵应支持交互浏览和筛选，至少包含 SRS ID、SRS 主题、SDD ID、设计项、下游入口、状态和说明列。
- 生成后应执行以下检查：
  - 每条有效 SRS 在 HTML 中均有对应行。
  - 状态为 Open 或 N/A 的行均有说明。
  - HTML 文件可在浏览器中正常打开，无渲染错误。
  - 与 Markdown 追溯矩阵内容一致，无遗漏或冲突。
- 检查结果应记录在实际操作步骤和 SDD CHECK 清单中。

### 5.7 步骤七：执行质量门禁检查

目标：在 SDD 进入评审或 SDS 前，使用门禁 checklist 进行系统性检查。

门禁检查至少包括：

| 门禁 | 检查重点 | 推荐 checklist |
| --- | --- | --- |
| Gate 1 架构输入门禁 | SRS、SDD 规范、标准、系统流程输入是否完整 | `Checklist-Gate1-架构输入完整性.md` |
| Gate 2 SRS 覆盖门禁 | 每条 SRS 是否被 SDD 覆盖、N/A 或开放项管理 | `Checklist-Gate2-SRS覆盖与追溯.md` |
| Gate 3 架构内容完整性门禁 | 职责、分层、接口、数据流、状态、配置、依赖等是否完整 | `Checklist-Gate3-架构内容完整性.md` |
| Gate 4 架构技术正确性门禁 | 接口、状态、错误、安全、多核、资源等设计是否正确可实施 | `Checklist-Gate4-架构技术正确性.md` |
| Gate 5 通用化与集成边界门禁 | 是否避免项目化固化，配置、Callout、依赖抽象是否清晰 | `Checklist-Gate5-通用化与集成边界.md` |
| Gate 6 SDS 输入充分性门禁 | SDD 是否足以支撑 SDS、Coding、IT/ST | `Checklist-Gate6-SDS输入充分性.md` |
| Gate 7 SDD 基线发布门禁 | 评审问题、开放项、交付包和发布条件是否闭环 | `Checklist-Gate7-SDD基线发布.md` |

### 5.8 步骤八：修正问题并闭环开放项

目标：对门禁检查发现的问题进行修正、回写 SRS、登记开放项或申请遗留批准。

问题处理规则：

| 问题类型 | 处理方式 |
| --- | --- |
| SRS 输入缺失 | 回写 SRS 问题清单或需求变更，不在 SDD 静默补齐 |
| SRS 未覆盖 | 补充 SDD 设计、说明 N/A 或登记开放项 |
| 设计无来源 | 删除、补充来源或形成批准的架构决策记录 |
| 接口语义不清 | 补充参数、返回值、同步/异步、前置后置和错误处理 |
| 状态语义不清 | 明确软件请求状态、软件记录状态、硬件确认状态或不可确认状态 |
| 诊断/错误边界不清 | 明确 DET、DEM、内部错误、返回值和失败后置条件 |
| 安全机制无来源 | 删除安全声明或补充安全需求/安全分析输入 |
| 项目化固化 | 改为配置、Callout、依赖抽象或集成约束 |
| 资源/时序缺失 | 补充预算、估算方法或后续测量计划 |
| 高影响开放项未关闭 | 不得进入基线，除非评审批准遗留且不阻塞 SDS |

### 5.9 步骤九：生成实际操作步骤与 CHECK 清单

目标：在 SDD 评审与基线前，形成与架构文档同路径归档的实际操作记录和最终 CHECK 清单，使架构生成过程可复现、可审计、可交接。

实际操作步骤 `Operation_Steps_SDD_[FC_SHORT_NAME].md` 应至少包含：

| 章节 | 内容要求 |
| --- | --- |
| 任务背景 | FC 模块名称、简称、目标、输入范围和输出路径 |
| 输入文件清单 | 实际使用的 SRS、规范、模板、系统文件、版本、章节、路径和适用性 |
| 执行步骤记录 | 按实际顺序记录输入索引、SRS 充分性确认、架构设计、追溯、门禁检查、问题修正和评审准备 |
| 关键判断依据 | 记录职责边界、接口固定、状态语义、配置/Callout 取舍、安全机制、项目化约束降级等判断理由 |
| 问题与处理 | 记录发现的问题、处理方式、责任人、关闭证据或遗留批准 |
| 输出文件清单 | 列出 SDD、Trace、Review、InterfaceSpec、TimingSpec、StateMachine、SafetyDesign、CHECK 清单等最终文件 |
| 剩余事项 | 记录遗留开放项、SDS 输入风险、需下游确认事项 |

SDD CHECK 清单 `CHECK_SDD_[FC_SHORT_NAME].md` 应至少包含：

| 章节 | 内容要求 |
| --- | --- |
| Gate 汇总 | Gate 1 至 Gate 7 的通过/不通过/有条件通过结论 |
| 检查项明细 | 复制或引用各 Gate checklist 的检查结果、问题记录和 N/A 理由 |
| 问题闭环表 | 问题 ID、来源、影响、处理方式、责任人、状态、关闭证据 |
| 开放项与遗留风险 | Open 项状态、影响分析、是否阻塞 SDS、批准人和关闭条件 |
| 发布包完整性 | 确认 SDD、实际操作步骤、CHECK 清单和过程产物均在同一输出路径 |
| 最终结论 | 是否允许进入 SDS、基线版本、评审人/批准人、日期 |

完成标准：

- `Operation_Steps_SDD_[FC_SHORT_NAME].md` 与 `CHECK_SDD_[FC_SHORT_NAME].md` 已生成。
- 两个文件与 `SDD_[FC_SHORT_NAME].md` 存放在同一输出路径。
- CHECK 清单覆盖 Gate 1 至 Gate 7，且每个 Fail 或有条件通过项均能追溯到问题记录或遗留批准。
- 实际操作步骤能够支持后续人员复现本次架构设计生成过程。

### 5.10 步骤十：SDD 评审与基线

目标：形成可进入 SDS 的 SDD 基线。

评审输出应包含：

- SDD 文档评审结论。
- 门禁 checklist 结果。
- 实际操作步骤记录。
- SDD CHECK 清单。
- SRS 到 SDD 追溯矩阵。
- 架构问题清单与关闭状态。
- 开放项清单与遗留风险批准状态。
- SDS 输入充分性结论。
- IT/ST 验证输入清单。

SDD 进入 SDS 的最低条件：

- 所有有效 SRS 均被 SDD 覆盖、说明 N/A 或经批准遗留。
- 模块职责、非职责、上下文、分层、文件结构和依赖边界明确。
- 所有对外接口的名称、参数、返回值、同步/异步、可重入性和错误处理明确。
- 数据流、状态机、配置、时序、资源、诊断、安全、多实例、多核和集成约束明确。
- 安全机制有来源、响应、降级路径和验证入口。
- SDD 不要求 SDS 或 Coding 自行补充未定义的软件行为。
- 高影响开放项已关闭，或经评审批准且不阻塞 SDS。

## 6 质量原则

### 6.1 SRS 驱动

SDD 只能细化、组织和分配 SRS 中已有的软件行为、接口能力、约束和安全要求。发现 SRS 缺失或矛盾时，应回写问题，不得静默补齐。

### 6.2 可追溯

每个架构决策、接口、状态机、安全机制和关键约束均应能追溯到 SRS、系统流程、标准规范、平台约束或批准的架构决策。

### 6.3 高层设计不过度下沉

SDD 应回答模块如何划分和集成，不展开私有函数逐行逻辑、局部变量级算法、单元测试步骤或代码实现细节。

### 6.4 通用化与项目适配分离

FC 架构应描述模块通用能力和稳定接口。项目一次性目录、任务名、板级接法、通道编号、OS 策略等应作为配置、Callout 或集成约束处理。

### 6.5 状态语义清晰

涉及状态或模式时，应明确区分：

- 软件请求状态
- 软件记录状态
- 硬件确认状态
- 状态不可确认

不得把“软件已请求”描述为“硬件已确认”。

### 6.6 下游可实施

SDD 应足以支持 SDS 编写、接口固定、代码结构规划、IT/ST 设计和追溯维护，不应停留在空泛原则。

## 7 与下游 SDS 的接口

SDD 交付给 SDS 前，应至少明确以下内容：

| SDS 输入项 | SDD 要求 |
| --- | --- |
| 模块职责 | 明确每个职责对应的架构项和下游设计入口 |
| 文件结构 | 明确 `.c/.h/_Types/_Cfg/_CfgData/_Callout/MemMap` 文件边界 |
| 对外接口 | 明确 API 名称、参数、返回值、前置后置、错误处理和可重入性 |
| 内部分层 | 明确各层职责、调用方向和禁止跨层访问规则 |
| 数据对象 | 明确配置数据、运行时数据、状态数据、诊断数据及保护策略 |
| 状态机 | 明确状态集合、事件、转移、动作、异常路径和安全状态 |
| 配置项 | 明确配置结构、范围、一致性规则、检测时机和失败行为 |
| 依赖/Callout | 明确下层依赖语义、失败反馈、Stub 策略和集成责任 |
| 错误处理 | 明确每类错误的检测位置、记录方式、对外行为和恢复策略 |
| 安全机制 | 明确故障假设、检测条件、故障响应、降级恢复和验证入口 |
| 多实例/多核 | 明确索引、隔离、共享资源、同步策略和非法访问行为 |
| 时序资源 | 明确周期、响应时间、资源预算或测量计划 |
| Memory Map | 明确对象类型与段宏映射关系 |
| 追溯入口 | 明确 SRS-SDD-SDS-Code-Test 的连接方式 |

## 8 禁止行为

FC SDD 编写过程中不得出现以下行为：

- 未经 SRS 或批准输入支撑新增功能。
- 将 SRS 缺失内容在 SDD 中静默补齐。
- 将芯片或平台存在能力自动写成本模块支持能力。
- 将单一项目的目录、任务、通道、板级接法或 OS 策略固化为 FC 通用架构。
- 使用“合理分层、适当处理、必要时、尽快、稳定”等不可验证表述替代设计内容。
- 只画图不说明接口、数据、状态和依赖语义。
- 设计无限等待或无边界重试。
- 宣称无来源安全机制或默认安全等级。
- 用 N/A 掩盖未覆盖 SRS，N/A 必须说明理由。
- 删除或复用已进入评审/追溯的 SDD ID。

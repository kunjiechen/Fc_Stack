# FC详细设计编写规范

## 1 目的

本文档用于规范 FC（Function Component）软件详细设计文档（SDS：Software Design Specification）的编写方法，确保详细设计能够承接 SRS 和 SDD，明确函数级处理逻辑、数据结构、状态分支、边界条件、错误路径、时序资源和验证入口，并作为 Coding、UT 和代码评审的直接输入依据。

FC 是独立的软件模块，详细设计应服务于可移植、可配置、可复用的模块实现。SDS 应细化模块的稳定函数职责、数据对象、分支路径和配置/Callout 适配点，而不是围绕某一个具体项目的临时实现细节展开。

本文档适用于 MCAL、BSW、IoExtDrv、CDD、ASW 等层级中 FC 模块的软件详细设计、评审和维护。

---

## 2 基本原则

### 2.1 SRS/SDD 驱动原则

SDS 应基于已评审或已基线化的 SRS、SDD、InterfaceSpec、StateMachine、TimingSpec、SafetyDesign 和 DataDict 编写。SDS 只能细化已批准的软件需求和架构设计，不得新增无来源功能、接口、状态或安全机制。

若详细设计阶段发现 SRS 或 SDD 缺失、矛盾、不可实现，应回写问题清单或变更项，不得在 SDS 中静默改变需求或架构语义。

### 2.2 函数级可实现原则

SDS 应描述到函数级、数据对象级和分支路径级，能够让开发人员在不自行补充设计意图的情况下编写代码。

每个函数级设计应明确：

- 函数职责。
- 关联 SRS/SDD。
- 调用前置条件。
- 输入、输出和返回值。
- 使用的数据对象和配置项。
- 处理步骤。
- 正常路径、边界路径和异常路径。
- 错误处理和诊断记录。
- 时序、资源和重入约束。
- UT 验证入口。

### 2.2A FC 复用导向原则

SDS 应细化“通用 FC 模块”的实现，而不是细化“某一具体项目定制件”的实现。函数职责、状态变量、配置结构、错误路径和接口语义应在迁移到不同项目时保持稳定；差异应主要体现在配置值、Callout 适配、依赖实现和集成前置条件上。

### 2.2B 集成差异隔离原则

若函数行为依赖 MCU、SoC、OS、硬件连接关系、板级极性、外部驱动返回值或集成调用时序，SDS 应明确这些差异是如何通过配置、Callout 或依赖抽象吸收的。

不得把仅在单一集成环境下成立的处理步骤、固定通道号、固定任务名、固定时序来源或固定硬件连接假设，直接写成 FC 内部函数的通用处理逻辑。

### 2.2C 可移植实现原则

SDS 中应明确区分：

- 通用函数逻辑
- 配置裁剪逻辑
- Callout/依赖适配逻辑
- 集成环境前置条件

从而使编码时能够保持一个可复用的软件模块主体，而将环境差异限制在最小范围内。

### 2.3 单一职责原则

一个 SDS 条目应描述一个函数、一个数据对象、一组强关联状态转移或一个明确算法单元。若一个设计条目包含多个独立功能，应拆分成多个 SDS 条目。

### 2.4 可测试原则

SDS 应能直接支持 UT 用例设计。每个关键分支、边界、异常、故障注入和安全响应均应有可观察结果或可检查内部状态。

SDS 中不得使用“适当处理”“合理判断”“必要时执行”“尽快返回”等无法测试的表述。

### 2.5 代码一致性原则

SDS 中定义的函数名、参数名、返回值、类型、枚举、宏、变量和文件结构应与 SDD、DataDict 和后续代码保持一致。进入编码后若发生变化，应同步更新 SDS 和追溯矩阵。

### 2.6 配置与适配分离原则

SDS 应把模块主体逻辑、配置裁剪逻辑和 Callout/依赖适配逻辑分开描述。

推荐做法：

- 主体逻辑描述与具体项目无关的处理流程
- 配置逻辑描述能力启用、范围校验和实例化方式
- Callout/依赖适配逻辑描述硬件差异、驱动差异或外部服务差异的吸收方式

这样在迁移到不同项目时，优先替换配置和适配层，而不是重写主体函数逻辑。

### 2.7 复用边界可验证原则

SDS 应能回答一个问题：当更换 MCU、OS、硬件连接方式或上层集成方式时，哪些函数逻辑保持不变，哪些仅通过配置或 Callout 变化。

若文档无法回答这个问题，通常说明 SDS 仍然写得过于项目化，不利于 FC 复用。

## 3 SDS 推荐结构

FC 模块 SDS 推荐包含以下章节：

1. 目的
2. 适用范围
3. 定义和缩写
4. 设计输入与追溯
5. 详细设计总览
6. 文件与函数清单
7. 数据字典与数据对象设计
8. 接口函数详细设计
9. 内部函数详细设计
10. 状态机与分支详细设计
11. 算法与处理流程详细设计
12. 配置与标定详细设计
13. 错误处理与诊断详细设计
14. 安全机制详细设计
15. 多实例、多核与重入详细设计
16. 时序与资源详细设计
17. Memory Map 与代码段设计
18. SDS 到代码与测试追溯
19. UT 设计输入
20. 详细设计评审检查清单
21. 支持/相关性文件

支持/相关性文件章节应放在文档最后。文件名称应只写文档名称，不写绝对路径；若需要路径，应在文档索引或追溯文件中维护。

## 4 SDS 编号规则

### 4.1 编号格式

推荐格式：

```text
SDS-[FC_SHORT_NAME]-[CATEGORY]-[NNNN]
```

示例：

```text
SDS-TJA1043-INTF-0001
SDS-TJA1043-FUNC-0001
SDS-TJA1043-DATA-0001
```

### 4.2 设计类别

| 类别 | 含义 | 示例 |
| --- | --- | --- |
| IF | 接口函数详细设计 | Init、MainFunction、Set/Get API |
| FUNC | 内部函数详细设计 | CheckParam、UpdateState、PackFrame |
| DATA | 数据对象详细设计 | 运行时上下文、错误标记、缓存 |
| TYPE | 类型/枚举/结构体设计 | ModeType、ConfigType、ContextType |
| STATE | 状态机和状态转移设计 | UNINIT/RUNNING/FAULT 转移 |
| ALG | 算法和处理流程设计 | CRC、滤波、重试、查表、计算 |
| CFG | 配置和标定详细设计 | 配置结构、配置校验、默认值 |
| DIAG | 诊断和错误处理设计 | DET、DEM、内部错误、硬件故障 |
| SAFE | 安全机制详细设计 | 安全状态、降级、监控 |
| CORE | 多实例、多核、重入设计 | Instance ID、Core ID、临界区 |
| TIM | 时序和资源设计 | 执行时间、周期、栈、CPU |
| MEM | Memory Map 和段设计 | Code/Const/Var section |
| UT | 单元测试输入设计 | 测试点、覆盖目标、桩函数 |

### 4.3 编号稳定性

SDS ID 一旦被代码注释、UT 用例或追溯矩阵引用，应保持稳定。删除 SDS 条目时，应在追溯矩阵中记录废止状态和替代条目，不建议复用原 ID。

## 6 第五章“详细设计总览”写法

### 6.1 模块详细设计摘要

| 项 | 内容 |
| --- | --- |
| 模块名称 | `[FC_MODULE_NAME]` |
| 模块简称 | `[FC_SHORT_NAME]` |
| 所属层级 | `[ASW/BSW/IoExtDrv/CDD/MCAL]` |
| 安全等级 | `[QM/ASIL A/B/C/D]` |
| 主要接口函数 | `[Init/MainFunction/Set/Get...]` |
| 主要内部函数 | `[Check/Update/Pack/Unpack...]` |
| 主要运行时数据 | `[Context/ErrorStatus/Buffer...]` |
| 主要配置数据 | `[Config/CfgData/Calibration...]` |
| 主要状态机 | `[StateMachine名称]` |
| 主要依赖 | `[Callout/MCAL/BSW服务]` |
| 主要适配点 | `[配置裁剪/Callout/依赖抽象]` |

### 6.2 详细设计分解图

推荐使用 ASCII 或 Mermaid 图说明从接口到内部函数的调用关系：

```text
[FC]_Init
  -> [FC]_CheckConfig
  -> [FC]_InitRuntime
  -> [FC]_Callout_InitDependency

[FC]_MainFunction
  -> [FC]_LoadRuntimeInput
  -> [FC]_UpdateStateMachine
  -> [FC]_ExecuteAction
  -> [FC]_StoreRuntimeOutput
```

### 6.3 详细设计边界

应说明 SDS 不覆盖或不展开的内容：

| 边界项 | 不展开原因 | 下游/外部依据 |
| --- | --- | --- |
| `[MCAL内部实现]` | `[供应商代码/平台已有实现]` | `[MCAL文档/接口规范]` |
| `[复杂算法外部库]` | `[由库提供]` | `[库规范/接口]` |
| `[集成环境适配细节]` | `[由配置/Callout吸收]` | `[SDD适配设计/集成规范]` |

| SDS ID | 数据名 | 类型 | 存储位置 | 配置时机 | 有效范围 | 失效处理 | 描述 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SDS-[FC]-CFG-0001 | `[FC]_Config` | `[const struct]` | `[Cfg.c]` | `[Pre/Post]` | `[范围]` | `[编译错误/E_NOT_OK]` | `[说明]` |

### 8.6 数据对象设计规则

- 局部变量使用前必须赋初值。
- 内部全局变量应在 Init 中初始化，不依赖编译器启动库隐式初始化。
- 大局部变量应避免放在栈上。
- 数组长度应使用具备语义的宏。
- 多实例数据应明确索引范围和越界处理。
- 共享数据应定义保护策略。
- 环境差异相关数据应优先通过配置对象或适配层接口表达，不应散落在主体逻辑中。

## 9 第八章“接口函数详细设计”写法

### 9.1 接口函数设计模板

每个接口函数应按以下结构编写。

#### SDS-[FC_SHORT_NAME]-IF-0001 `[FunctionName]`

| 属性 | 内容 |
| --- | --- |
| 函数名称 | `[FunctionName]` |
| 函数类型 | Interface Function |
| 所属文件 | `[FC_SHORT_NAME].c/.h` |
| 关联 SRS | `[SRS-ID]` |
| 关联 SDD | `[SDD-ID]` |
| 同步/异步 | `[Synchronous/Asynchronous]` |
| 可重入性 | `[Reentrant/Non-Reentrant]` |
| 参数 in | `[参数名、类型、范围、含义]` |
| 参数 inout | `[参数名、类型、范围、含义]` |
| 参数 out | `[参数名、类型、范围、空指针行为]` |
| 返回值 | `[返回值及语义]` |
| 前置条件 | `[初始化/配置/状态/调用上下文]` |
| 后置条件 | `[成功和失败后的状态]` |
| 使用数据 | `[变量/配置/状态]` |
| 调用函数 | `[内部函数/Callout]` |
| 错误处理 | `[DET/内部错误/返回值/DEM]` |
| 时序约束 | `[执行时间/调用周期/阻塞限制]` |
| UT 入口 | `[UTS-ID 或待分配]` |
| 适配边界 | `[哪些差异通过配置或 Callout 吸收]` |

**处理逻辑**：

```text
1. [初始化局部变量和返回值]
2. [检查模块初始化状态]
3. [检查输入参数范围]
4. [检查输出指针]
5. [读取或写入运行时数据]
6. [调用内部处理函数或 Callout]
7. [设置返回值和输出参数]
8. [返回]
```

**分支与边界**：

| 条件 | 处理 | 返回值/输出 | 诊断/错误标记 | UT 用例 |
| --- | --- | --- | --- | --- |
| `[正常输入]` | `[执行功能]` | `[E_OK/输出]` | `[无]` | `[UTS-ID]` |
| `[未初始化]` | `[不执行功能]` | `[E_NOT_OK]` | `[DET/错误标记]` | `[UTS-ID]` |
| `[空指针]` | `[不写输出]` | `[E_NOT_OK]` | `[DET/错误标记]` | `[UTS-ID]` |
| `[无效ID]` | `[不执行功能]` | `[E_NOT_OK]` | `[DET/错误标记]` | `[UTS-ID]` |

### 9.2 接口函数设计规则

- 接口函数应执行外部输入防御性检查。
- 参数检查失败时不应执行功能动作。
- 返回值应优先初始化为失败状态，再在成功路径设置为成功。
- 输出参数只有在检查通过且输出有效时写入。
- MainFunction 若无返回值，应通过内部状态、诊断或测试观察点验证。
- DET 关闭时的行为应在 SDD/SDS 中保持一致。
- 接口函数不应把单一项目的硬件连接假设直接写死在主体流程中，应通过配置或 Callout 适配。

## 22 常见问题

### 22.1 SDS 可以改变 SDD 中的接口吗？

不可以静默改变。若 SDS 阶段发现接口不可实现或存在矛盾，应提出 SDD 问题或变更。SDS 只能细化接口函数内部处理逻辑。

### 22.2 内部函数是否需要和接口函数一样做参数检查？

通常不需要。接口函数负责外部输入防御性检查；内部函数的调用时序和参数有效性由设计和测试保证。若内部函数被多个复杂路径调用且存在真实边界风险，应在前置条件或内部检查设计中说明。

### 22.3 SDS 是否需要写代码？

SDS 不应写成完整 C 代码，但应提供足够明确的伪代码、分支表和数据对象设计，使编码不存在设计歧义。

### 22.4 代码注释关键字和 SDS 是什么关系？

代码中的类型、变量、接口函数、内部函数注释关键字应能被工具提取并回溯到 SDS 设计项。若代码对象无法映射到 SDS，应补充 SDS 或删除无来源代码。

### 22.5 某些资源数值无法在 SDS 阶段确认怎么办？

可以标记为“集成阶段评估并记录”，但应说明评估方式、验证阶段和责任入口，不得编造阈值。

### 22.6 如何避免把 SDS 写成单项目定制实现？

应明确函数主体逻辑、配置逻辑和 Callout/依赖适配逻辑的边界。

判断标准是：当更换 MCU、OS、硬件连接方式或外部驱动实现时，主体函数步骤大体不变，主要变化落在配置值、适配函数和集成前置条件上。若每次集成都需要改写主体流程，说明 SDS 设计仍然过于项目化。

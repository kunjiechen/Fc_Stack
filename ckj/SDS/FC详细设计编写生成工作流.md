# FC详细设计编写生成工作流

## 1 目的

本文档定义 FC（Function Component）软件详细设计规范（SDS）的生成工作流，用于指导从已完成的软件架构设计、详细设计编写规范、模板、文档标准和系统流程约束中生成完整、可编码、可验证、可追溯的软件详细设计文档。

本工作流适用于 FcStack 中 MCAL、BSW、IoExtDrv、CDD、ASW 等 FC 模块的软件详细设计、评审和进入 Coding 阶段前的质量门禁。

## 2 输入范围

FC 详细设计编写生成应至少使用以下输入：

| 输入类别 | 推荐位置 | 用途 |
| --- | --- | --- |
| SDD 架构设计 | `Output/[FC_SHORT_NAME]/Doc/SDD/` | 提供模块职责、接口、状态、配置、依赖、诊断、安全、时序、资源和集成边界输入 |
| SDS 编写规范与模板 | `Standard/RuleAndTemplate/SDS/` | 约束 SDS 文档结构、详细设计内容、编号、评审和模板格式 |
| 文档类标准规范 | `Standard/Conversion/Doc/` | 约束文档质量、图表表达、评审规则和阶段出口要求 |
| 系统流程与系统输入 | `System/` | 约束 V 模型阶段出口、追溯、评审、变更、编码输入和验证入口要求 |

若 SDD、标准规范或系统输入不足以支撑确定性详细设计，应登记开放项并回写 SDD 问题清单，不得在 SDS 中静默补齐关键架构决策或未定义的软件行为。

## 3 输出范围

FC 详细设计完成后，最终输出至少包含以下文件：

| 输出物 | 文件名建议 | 推荐位置 | 说明 |
| --- | --- | --- | --- |
| 模块详细设计规范文档 | `SDS_[FC_SHORT_NAME].md` 或项目约定名称 | `Output/[FC_SHORT_NAME]/Doc/SDS/` 或项目约定 SDS 输出目录 | 正式 FC 软件详细设计规范，承载函数、数据、状态、配置、错误、时序、Memory Map、验证入口等详细设计内容 |
| 架构设计-详细设计追溯矩阵 | `Trace_SDD_SDS_[FC_SHORT_NAME].md` 或项目约定名称 | `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/` | 记录每条关键 SDD 设计项如何被 SDS 设计项覆盖、N/A 或保持开放 |

详细设计最终输出目录只要求存放模块详细设计规范文档，不要求将输入索引、独立 DataDict、SDS 到 Code/UT 追溯、评审记录、实际操作步骤、CHECK 清单等辅助产出归档到最终输出目录。

若项目或评审活动需要上述辅助材料，可在工作过程、评审记录、临时工作区或项目另行约定的位置维护；其中详细设计正文应保留必要摘要或入口，确保 Coding、UT、评审和追溯能够继续执行。

## 4 工作流总览

```text
详细设计输入收集与索引
    ↓
SDD 输入充分性确认
    ↓
文件与数据对象设计
    ↓
接口函数与内部函数详细设计
    ↓
状态机、配置、错误、安全、资源与并发细化
    ↓
建立 SDD → SDS 追溯并准备 Code/UT 入口
    ↓
质量门禁检查
    ↓
问题修正与开放项闭环
    ↓
整理最终输出与评审结论
    ↓
SDS 评审与基线
    ↓
进入 Coding 阶段
```

## 5 工作步骤

### 5.1 步骤一：建立详细设计输入索引

目标：明确 SDS 生成所依赖的全部输入资料，确保每项输入都有明确用途和可追溯位置。

详细设计输入索引应至少包含以下信息。索引可写入 SDS 设计输入章节，也可在工作过程中单独维护；除非项目另有约定，不作为最终输出目录必存文件。

| 字段 | 说明 |
| --- | --- |
| 输入ID | 如 `DIN-[FC_SHORT_NAME]-0001` |
| 文件名称 | 输入文件名称，不写绝对路径 |
| 输入类型 | SDD、InterfaceSpec、StateMachine、SafetyDesign、标准规范、系统输入等 |
| 章节/位置 | 可追溯到具体章节、标题、页码、设计项 ID 或图表 |
| 版本/日期 | 若输入资料提供版本，应记录 |
| 是否适用 | 是/否/部分适用/待确认 |
| 适用说明 | 说明该输入对 SDS 的作用 |
| 预期设计类别 | FILE/IF/FUNC/DATA/TYPE/STATE/ALG/CFG/DIAG/SAFE/CORE/TIM/MEM/UT |

完成标准：

- `Output/[FC_SHORT_NAME]/Doc/SDD/` 中与当前 FC 相关的架构设计输入已登记。
- `Standard/RuleAndTemplate/SDS/` 中 SDS 编写规范、模板和 Checklist 已登记。
- `Standard/Conversion/Doc/` 中适用的文档规范和质量标准已登记。
- `System/` 中 V 模型、阶段出口、追溯、编码输入和验证约束已登记。
- 不适用输入已说明 N/A 原因。

### 5.2 步骤二：确认 SDD 输入充分性

目标：确认 SDD 足以支撑 SDS 细化，避免详细设计阶段自行定义关键架构行为。

应检查 SDD 是否至少明确：

| 输入项 | SDS 使用方式 |
| --- | --- |
| 模块职责 | 固化 SDS 的设计边界和非设计边界 |
| 文件结构 | 指导 `.c/.h/_Types/_Cfg/_CfgData/_Callout/_MemMap` 文件职责划分 |
| 对外接口 | 固化 API 名称、参数、返回值、前后置条件、同步/异步和可重入性 |
| 状态机 | 细化状态变量、转移条件、动作、异常状态和恢复路径 |
| 配置模型 | 细化配置对象、配置校验、一致性规则和失效处理 |
| 依赖与 Callout | 细化下层接口、返回语义、失败路径和桩函数入口 |
| 错误与诊断 | 细化错误标记、DET/DEM、返回值和故障响应路径 |
| 安全边界 | 细化故障检测、降级、安全状态和验证入口 |
| 资源与时序 | 细化周期、触发、阻塞、超时、局部资源和预算输入 |
| 多实例/多核 | 细化 Instance ID、Core ID、共享数据保护和并发策略 |
| 追溯入口 | 建立 SDD ID 到 SDS/Code/UT 的关联入口 |

处理规则：

- SDD 输入明确时，进入详细设计。
- SDD 输入缺失但不影响主线细化时，登记开放项并标注不阻塞原因。
- SDD 输入缺失且影响接口、状态、安全、配置、错误处理、并发或验证时，不得继续固化设计，应回写 SDD 问题或架构变更。

### 5.3 步骤三：设计文件结构与数据对象

目标：建立可编码的文件边界、类型体系、数据对象和配置载体。

应生成以下内容：

| 内容 | 要求 |
| --- | --- |
| 文件清单 | 明确 `.c/.h/_Types/_Cfg/_CfgData/_Callout/_MemMap` 等文件及职责 |
| 类型设计 | 枚举、typedef、结构体、宏值域、错误位、状态位等均有定义 |
| 运行时对象 | 明确名称、类型、作用域、生命周期、初值、读写者和保护策略 |
| 配置对象 | 明确配置宏、配置结构、配置表、默认值、范围、一致性校验和失效行为 |
| Memory Map | 明确函数、常量、变量和配置对象对应的 Section 宏和适用文件 |
| 数据字典内容 | 为 Coding、UT 和追溯提供类型、对象、配置和 Memory Section 入口；可纳入 SDS，不强制独立成文 |

设计规则：

- 数据对象命名应符合项目命名规范。
- 运行时数据、配置数据和常量数据应分离描述。
- 多实例、多核或共享数据必须显式定义保护策略。
- 不得依赖“默认已初始化”或“实现时再定”之类模糊假设。

### 5.4 步骤四：设计接口函数与内部函数

目标：将架构设计细化到函数级、分支级和错误路径级，确保开发者无需自行补充关键设计。

接口函数设计应至少包含：

| 字段 | 要求 |
| --- | --- |
| SDS ID | 如 `SDS-[FC_SHORT_NAME]-IF-0001` |
| 函数名称 | 与 SDD/接口规范保持一致 |
| 关联 SRS/SDD | 记录来源需求和架构设计项 |
| 参数/返回值 | 名称、方向、类型、范围、空指针规则、返回语义 |
| 前置/后置条件 | 初始化、状态、配置、调用上下文和成功/失败后置条件 |
| 处理逻辑 | 可编码的步骤化逻辑 |
| 分支/边界/异常 | 正常路径、边界路径、异常路径和错误路径 |
| 调用依赖 | 内部函数、Callout、下层服务和调用条件 |
| 诊断/安全 | 错误上报、错误标记、安全响应和恢复入口 |
| UT 入口 | 对应测试对象、覆盖目标和故障注入入口 |

内部函数设计规则：

- 关键内部函数应具备独立 SDS ID 和完整职责描述。
- 内部函数不重复接口层已完成的防御性检查，除非 SDD 明确要求。
- 若分支复杂度过高，应拆分函数并保留清晰调用关系。
- 与集成环境强相关的差异应优先下沉到配置或 Callout，而不是散落在主体逻辑中。

### 5.5 步骤五：细化状态、配置、错误、安全和资源设计

目标：确保 SDS 不只描述主路径，还完整覆盖编码和 UT 所需的边界、异常和约束。

应至少细化以下内容：

| 设计类别 | 细化要求 |
| --- | --- |
| 状态机 | 状态变量、初始状态、事件、条件、动作、下一状态、非法状态和恢复路径 |
| 配置校验 | 空指针、范围越界、一致性错误、实例数量、通道映射和失败处理 |
| 错误路径 | 未初始化、无效 ID、无效模式、依赖失败、核不一致和配置错误 |
| 诊断设计 | DET/DEM/Event ID、错误标记、清除条件和上报位置 |
| 安全设计 | 故障检测、故障响应、降级、安全状态、恢复条件和故障注入入口 |
| 多实例/多核 | Instance ID/Core ID 映射、共享数据保护、临界区和可重入性 |
| 时序/资源 | 周期、触发、超时、阻塞、CPU/RAM/ROM/Stack 影响和估算方法 |
| 条件编译 | DET、MCAL、Core Enable、配置裁剪和平台分支的适用规则 |

### 5.6 步骤六：建立追溯并准备下游输入

目标：形成从架构设计到详细设计，再到代码和 UT 的连续追溯链。

应至少建立：

| 追溯方向 | 要求 |
| --- | --- |
| SDD → SDS | 每个关键设计项关联至少一个 SDS ID 或说明 N/A；完成后形成架构设计-详细设计追溯矩阵并存放到 `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/` |
| SDS → Code | 在 SDS 中为关键设计项预留代码文件、函数、变量、类型或配置对象入口 |
| SDS → UT | 在 SDS 中为关键函数、分支、错误路径和故障路径预留 UT 覆盖入口 |
| SRS → SDD → SDS | 对高风险需求保留纵向追溯链 |

处理规则：

- 架构设计-详细设计追溯矩阵应独立归档到 `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/`。
- SDS 到 Code、SDS 到 UT 追溯可在 SDS 中保留摘要入口；若项目需要独立成文，应存放到项目约定位置，不要求进入 SDS 最终输出目录。
- N/A 必须给出原因，不得用 N/A 掩盖漏项。
- Coding 和 UT 输入不足时，应回到 SDS 或 SDD 修正。

### 5.7 步骤七：执行质量门禁检查

目标：在 SDS 进入评审或 Coding 前，使用门禁 checklist 执行系统性检查。

门禁检查至少包括：

| 门禁 | 检查重点 | 推荐 checklist |
| --- | --- | --- |
| Gate 1 详细设计输入门禁 | 输入是否完整、适用性是否明确 | `Checklist-Gate1-详细设计输入完整性.md` |
| Gate 2 SDD 覆盖与追溯门禁 | SDD 是否被完整覆盖并建立追溯 | `Checklist-Gate2-SDD覆盖与追溯.md` |
| Gate 3 详细设计内容完整性门禁 | 文件、数据、函数、状态、配置等是否完整 | `Checklist-Gate3-详细设计内容完整性.md` |
| Gate 4 详细设计技术正确性门禁 | 设计语义、分支、错误、安全、并发是否正确 | `Checklist-Gate4-详细设计技术正确性.md` |
| Gate 5 通用化与适配边界门禁 | 是否保持 FC 通用化并隔离集成差异 | `Checklist-Gate5-通用化与适配边界.md` |
| Gate 6 Coding 输入充分性门禁 | SDS 是否达到 Coding Ready 条件 | `Checklist-Gate6-Coding输入充分性与CodingReady.md` |
| Gate 7 SDS 基线发布门禁 | 评审、开放项、记录和发布结论是否闭环 | `Checklist-Gate7-SDS基线发布.md` |

### 5.8 步骤八：修正问题并闭环开放项

目标：对门禁检查发现的问题进行修正、回写、删除、补充来源或转开放项。

问题处理规则：

| 问题类型 | 处理方式 |
| --- | --- |
| SDD 输入缺失 | 回写 SDD 补充设计，必要时回写 SRS |
| SDS 无法编码 | 补充文件、函数、数据、分支、错误或 UT 入口设计 |
| 追溯不完整 | 补充 SDD→SDS 追溯矩阵，并在 SDS 中补充 Code/UT 入口 |
| 通用化边界不清 | 将环境差异下沉到配置、Callout 或集成约束 |
| 安全/诊断边界不清 | 补充故障检测、上报、降级、安全状态和恢复策略 |
| CodingReady 不通过 | 不得进入 Coding，除非经评审批准且不阻塞编码主线 |

### 5.9 步骤九：整理最终输出与评审结论

目标：在 SDS 评审与基线前，收敛正式输出和必要评审结论，使最终目录清晰，追溯入口明确。

最终输出整理应至少确认：

| 检查项 | 要求 |
| --- | --- |
| SDS 文档 | 模块详细设计规范文档已完成，且包含可支撑 Coding、UT 和评审的详细设计内容 |
| SDD→SDS 追溯 | 架构设计-详细设计追溯矩阵已生成并存放到 `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/` |
| 辅助过程材料 | 输入索引、DataDict、Code/UT 追溯、操作步骤、CHECK 清单等若单独生成，应按项目约定保存，不要求进入 SDS 最终输出目录 |
| 评审结论 | Gate 结论、开放项、遗留风险、是否允许进入 Coding 已在评审记录或 SDS 评审章节中明确 |
| 下游入口 | SDS 中已保留 Code、UT、配置、Memory Map 和验证入口，开发者无需补充关键设计意图 |

### 5.10 步骤十：SDS 评审与基线

目标：形成可进入 Coding 的 SDS 基线。

评审输出应至少包含：

- SDS 文档评审结论。
- Gate checklist 结果或等效检查结论。
- 问题清单与关闭状态。
- 开放项清单与遗留风险批准状态。
- Coding 输入充分性结论。
- `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/` 中架构设计-详细设计追溯矩阵入口。

SDS 进入 Coding 的最低条件：

- 所有阻塞编码的开放项已关闭，或经评审批准遗留。
- 每个对外接口、关键内部函数、关键数据对象和关键错误路径均已设计。
- 数据字典内容、Memory Map、配置对象、Callout 边界和条件编译规则明确。
- 架构设计-详细设计追溯矩阵已生成；SDS 到 Code 和 SDS 到 UT 的入口已在 SDS 中建立。
- Coding Ready 检查通过，开发者不需要自行补充关键设计意图。

## 6 质量原则

### 6.1 架构驱动

SDS 只能细化已批准的 SDD、SRS 和系统输入，不得静默改变架构语义、接口原型、安全边界或验证结论。

### 6.2 函数级可编码

每个关键接口函数和内部函数都应提供可直接编码的步骤化设计，避免实现阶段依赖个人猜测。

### 6.3 单一职责

一个 SDS 设计项应描述一个函数、一个数据对象、一组强关联状态转移或一个明确算法单元；职责过宽时应拆分。

### 6.4 边界与异常完整

SDS 不仅描述正常路径，还必须覆盖边界、异常、错误、诊断、安全、故障注入和恢复路径。

### 6.5 通用化与适配隔离

SDS 应保持 FC 主体逻辑的通用化，将平台差异、项目差异和硬件差异下沉到配置、Callout 或集成约束。

### 6.6 可验证

每个关键设计项都应预留 Review、Analysis、UT、IT 或 ST 的验证入口，避免出现“实现后再看”的不可验证设计。

## 7 与下游 Coding 的接口

SDS 交付给 Coding 前，应至少明确以下内容：

| Coding 输入项 | SDS 要求 |
| --- | --- |
| 文件清单 | 明确需创建或修改的文件及文件职责 |
| API 设计 | 明确函数名、参数、返回值、前置条件、后置条件、同步/异步和重入性 |
| 内部函数 | 明确关键内部函数职责、调用关系和处理逻辑 |
| 数据对象 | 明确运行时对象、配置对象、常量对象和保护策略 |
| 状态机 | 明确状态变量、转移条件、动作和异常路径 |
| 错误处理 | 明确参数错误、配置错误、依赖失败、安全故障和诊断路径 |
| 条件编译 | 明确配置裁剪、DET、平台宏、多核开关等规则 |
| Memory Map | 明确 Code、Var、Const、Cfg 的 Section 宏和适用文件 |
| 追溯入口 | 明确 SDS 到代码、UT 和上游 SDD/SRS 的关联入口；架构设计-详细设计追溯矩阵归档到 `Output/[FC_SHORT_NAME]/Doc/TraceMatrix/` |
| UT 输入 | 明确正常、边界、异常和故障注入的测试入口和预期结果 |

## 8 禁止行为

FC SDS 编写过程中不得出现以下行为：

- 在无来源支撑下新增函数、数据对象、接口、状态或安全机制。
- 在 SDS 中静默修改 SDD 已固定的 API、状态语义或配置边界。
- 用“实现时决定”“编码时补充”“按经验处理”等语句替代确定设计。
- 用 N/A 掩盖遗漏，N/A 必须说明原因。
- 把单一项目临时适配直接固化为 FC 通用主体逻辑。
- 跳过数据字典内容、Memory Map、错误路径或 UT 入口设计。
- 未经评审批准就将 CodingReady 不通过的 SDS 交给 Coding。

# FC需求编写生成工作流

## 1 目的

本文档定义 FC（Function Component）软件需求规范（SRS）的生成工作流，用于指导从输入资料、需求编写规范、模板和系统流程约束中生成完整、准确、可验证、可追溯的软件需求文档。

本工作流适用于 FcStack 中 MCAL、BSW、IoExtDrv、CDD、ASW 等 FC 模块的软件需求编写、评审和进入 SDD 阶段前的质量门禁。

## 2 输入范围

FC 需求编写生成应至少使用以下输入：

| 输入类别 | 推荐位置 | 用途 |
| --- | --- | --- |
| 原始需求与技术资料 | `Input/<FC_SHORT_NAME>/Conversion/` | 提取模块职责、功能能力、接口、硬件约束、系统约束 |
| SRS 编写规范与模板 | `Standard/RuleAndTemplate/SRS/` | 约束文档结构、需求属性、编号、质量检查和模板格式 |
| 系统流程与 V 模型约束 | `System/` | 约束阶段出口、追溯、评审、验证和下游输入要求 |

若输入资料不足以支撑确定性需求，应登记开放项，不得补写无来源支撑的确定性需求。

## 3 输出范围

FC 需求编写阶段建议输出以下文件：

| 输出物 | 文件名建议 | 说明 |
| --- | --- | --- |
| 输入资料索引 | `Source_Index_[FC_SHORT_NAME].md` | 记录所有输入文件、章节、适用性和来源 ID |
| 来源内容抽取表 | `Source_Extract_[FC_SHORT_NAME].md` | 从输入资料中抽取原始需求、约束、事实和待确认内容 |
| 需求推导矩阵 | `Requirement_Derivation_[FC_SHORT_NAME].md` | 记录来源内容如何转化为 SRS 需求、N/A 或开放项 |
| 软件需求规范 | `SRS_[FC_SHORT_NAME].md` | 正式 FC 软件需求规范 |
| 需求追溯矩阵 | `Trace_SRS_[FC_SHORT_NAME].md` | 来源到 SRS 的初始追溯入口 |
| SRS 评审记录 | `Review_SRS_[FC_SHORT_NAME].md` | 记录门禁检查、问题、结论和遗留风险 |
| 实际操作步骤 | `Operation_Steps_SRS_[FC_SHORT_NAME].md` | 记录本次 SRS 生成的实际执行步骤、输入文件、关键判断、生成命令或人工操作、问题处理和输出文件路径 |
| SRS CHECK 清单 | `CHECK_SRS_[FC_SHORT_NAME].md` | 汇总 Gate 1 至 Gate 6 的检查结果、问题、责任人、关闭状态和最终发布结论 |

上述输出物应存放在与需求文档 `SRS_[FC_SHORT_NAME].md` 相同的输出路径下。若项目约定输出目录为 `Output/[FC_SHORT_NAME]/Doc/SRS/` 或其他路径，则实际操作步骤和 SRS CHECK 清单必须与需求文档同目录归档，不得散落在临时目录或工具目录中。

## 4 工作流总览

```text
输入资料收集
    ↓
输入资料索引
    ↓
来源内容抽取
    ↓
需求推导与分类
    ↓
SRS 文档生成
    ↓
质量门禁检查
    ↓
问题修正与开放项闭环
    ↓
生成实际操作步骤与 CHECK 清单
    ↓
SRS 评审与基线
    ↓
进入 SDD 阶段
```

## 5 工作步骤

### 5.1 步骤一：建立输入资料索引

目标：明确 SRS 生成所依赖的全部输入资料，确保每项来源都有唯一来源 ID。

输入资料索引应至少包含：

| 字段 | 说明 |
| --- | --- |
| 来源ID | 如 `SRC-[FC_SHORT_NAME]-0001` |
| 文件名称 | 输入文件名称，不写绝对路径 |
| 文件类型 | 原始需求、技术手册、系统约束、安全输入、标准规范等 |
| 章节/位置 | 可追溯到具体章节、标题、页码或段落 |
| 版本/日期 | 若输入资料提供版本，应记录 |
| 是否适用 | 是/否/部分适用/待确认 |
| 适用说明 | 说明该来源与 FC 模块的关系 |
| 预期需求类别 | FUNC/INTF/CFG/INIT/MODE/DIAG/SAFE/ERR/TIM/RES/COMP |

完成标准：

- 所有 `Input/<FC_SHORT_NAME>/Conversion/` 中与当前 FC 有关的输入均已登记。
- SRS 规范、模板和系统流程约束已作为规则来源登记。
- 不适用输入已说明 N/A 原因。

### 5.2 步骤二：抽取来源内容

目标：从输入资料中抽取可转化为软件需求的事实、约束、接口、状态、异常和待确认问题。

来源内容抽取表应至少包含：

| 字段 | 说明 |
| --- | --- |
| 抽取ID | 如 `EXT-[FC_SHORT_NAME]-0001` |
| 来源ID | 对应输入资料索引中的来源 ID |
| 原文/摘要 | 保留关键原文或准确摘要 |
| 内容类型 | 功能、接口、配置、状态、诊断、安全、时序、资源、约束、开放项 |
| 软件相关性 | 与 FC 对外行为、接口语义、配置或约束的关系 |
| 确定性 | 确定/待确认/冲突/不适用 |
| 备注 | 记录疑问、冲突或推导限制 |

抽取原则：

- 只抽取会影响软件对外行为、接口、配置、状态、诊断、安全、时序、资源或验证的内容。
- 芯片支持的能力不自动等同于 FC 软件需求。
- 原始输入中的项目一次性适配内容，应标记为集成约束或配置约束，不直接固化为 FC 通用需求。
- 无法确认的内容应进入开放项，不得改写为确定结论。

### 5.3 步骤三：进行需求推导与分类

目标：将来源抽取内容转化为 SRS 需求、N/A 说明或开放项。

需求推导矩阵应至少包含：

| 字段 | 说明 |
| --- | --- |
| 推导ID | 如 `DRV-[FC_SHORT_NAME]-0001` |
| 抽取ID | 对应来源内容抽取表 |
| 推导结论 | 生成需求/合并需求/拆分需求/N/A/开放项 |
| 需求类别 | FUNC/INTF/CFG/INIT/MODE/DIAG/SAFE/ERR/TIM/RES/COMP |
| 拟定 SRS ID | 如 `SRS-[FC_SHORT_NAME]-FUNC-0001` |
| 推导说明 | 说明为什么这样转化 |
| 风险/待确认 | 记录不确定性和下游影响 |

推导规则：

- 一个来源内容可拆分为多条需求。
- 多个来源内容可合并支撑一条需求，但必须全部保留来源。
- 每条需求只描述一个可验证行为或约束。
- 无来源支撑的想法不得进入 SRS 正文，只能作为开放项或删除。
- 需求类别应覆盖功能、接口、配置、初始化、模式、诊断、安全、异常、时序、资源和合规。

### 5.4 步骤四：生成 SRS 文档

目标：基于 `Template-FC模块软件需求规范.md` 生成完整 SRS 文档。

SRS 文档应至少包含：

1. 目的
2. 适用范围
3. 定义和缩写
4. 概述
5. 软件需求
6. 非功能需求
7. 约束与假设
8. 需求追溯
9. 验证策略
10. SRS 评审检查清单
11. 附录A 需求条目清单
12. 支持/相关性文件

每条需求必须包含以下属性：

| 属性 | 要求 |
| --- | --- |
| 需求ID | 唯一、稳定、符合编号规则 |
| 需求标题 | 简短说明需求主题 |
| 需求描述 | 使用“应/不得/应能够”，描述单一可验证行为 |
| 需求来源 | 明确来源 ID、章节、标准条款或约束来源 |
| ASIL等级 | QM/ASIL A/B/C/D；未知时标记待安全确认 |
| 前置条件 | 需求成立前应满足的条件 |
| 触发条件 | API 调用、周期任务、状态变化、故障条件等 |
| 输入 | 参数、信号、配置、状态或硬件反馈 |
| 输出 | 返回值、输出参数、状态变化、诊断记录或控制输出 |
| 异常/边界条件 | 无效参数、越界、未初始化、配置错误、状态不可确认等 |
| 验证方式 | Review/Analysis/Test/Inspection |
| 验证阶段 | SRS/SDD/Coding/UT/IT/ST |
| 状态 | Draft/Review/Baselined/Deprecated 等 |

### 5.5 步骤五：执行质量门禁检查

目标：在 SRS 进入评审或 SDD 前，使用门禁 checklist 进行系统性检查。

门禁检查至少包括：

| 门禁 | 检查重点 | 推荐 checklist |
| --- | --- | --- |
| Gate 1 输入来源门禁 | 输入资料是否完整、适用性是否明确 | `Checklist-Gate1-输入来源完整性.md` |
| Gate 2 来源覆盖门禁 | 来源是否全部处理、需求是否有来源 | `Checklist-Gate2-来源覆盖与追溯.md` |
| Gate 3 需求完整性门禁 | 需求类别和属性是否完整 | `Checklist-Gate3-需求内容完整性.md` |
| Gate 4 需求质量门禁 | 单条需求是否可验证、清晰、无歧义 | `Checklist-Gate4-需求质量.md` |
| Gate 5 SDD 输入门禁 | SRS 是否足以进入架构设计 | `Checklist-Gate5-SDD输入充分性.md` |
| Gate 6 基线发布门禁 | 开放项、评审问题和遗留风险是否闭环 | `Checklist-Gate6-SRS基线发布.md` |

### 5.6 步骤六：修正问题并闭环开放项

目标：对门禁检查发现的问题进行修正、删除、补充来源或转开放项。

问题处理规则：

| 问题类型 | 处理方式 |
| --- | --- |
| 需求无来源 | 删除、补充来源或转开放项 |
| 来源未覆盖 | 补充需求、说明 N/A 或登记开放项 |
| 需求不可验证 | 拆分、重写、补充输入输出和验证方式 |
| 需求过度设计 | 删除实现细节，保留对外行为和约束 |
| 状态语义不清 | 明确软件请求状态、软件记录状态、硬件确认状态或不可确认状态 |
| 安全等级未知 | 登记待安全确认开放项，不得默认 QM 或 ASIL |
| 高影响开放项未关闭 | 不得进入基线，除非评审批准遗留 |

### 5.7 步骤七：生成实际操作步骤与 CHECK 清单

目标：在 SRS 评审与基线前，形成与需求文档同路径归档的实际操作记录和最终 CHECK 清单，使需求生成过程可复现、可审计、可交接。

实际操作步骤 `Operation_Steps_SRS_[FC_SHORT_NAME].md` 应至少包含：

| 章节 | 内容要求 |
| --- | --- |
| 任务背景 | FC 模块名称、简称、目标、输入范围和输出路径 |
| 输入文件清单 | 实际使用的输入文件、版本、章节、路径和适用性 |
| 执行步骤记录 | 按实际顺序记录资料索引、内容抽取、需求推导、SRS 生成、门禁检查、问题修正和评审准备 |
| 关键判断依据 | 记录需求合并/拆分、N/A、开放项、ASIL/QM、通用能力与项目约束区分等判断理由 |
| 问题与处理 | 记录发现的问题、处理方式、责任人、关闭证据或遗留批准 |
| 输出文件清单 | 列出 SRS、Trace、Review、Source Index、Source Extract、Derivation、CHECK 清单等最终文件 |
| 剩余事项 | 记录遗留开放项、SDD 输入风险、需下游确认事项 |

SRS CHECK 清单 `CHECK_SRS_[FC_SHORT_NAME].md` 应至少包含：

| 章节 | 内容要求 |
| --- | --- |
| Gate 汇总 | Gate 1 至 Gate 6 的通过/不通过/有条件通过结论 |
| 检查项明细 | 复制或引用各 Gate checklist 的检查结果、问题记录和 N/A 理由 |
| 问题闭环表 | 问题 ID、来源、影响、处理方式、责任人、状态、关闭证据 |
| 开放项与遗留风险 | Open 项状态、影响分析、是否阻塞 SDD、批准人和关闭条件 |
| 发布包完整性 | 确认需求文档、实际操作步骤、CHECK 清单和过程产物均在同一输出路径 |
| 最终结论 | 是否允许进入 SDD、基线版本、评审人/批准人、日期 |

完成标准：

- `Operation_Steps_SRS_[FC_SHORT_NAME].md` 与 `CHECK_SRS_[FC_SHORT_NAME].md` 已生成。
- 两个文件与 `SRS_[FC_SHORT_NAME].md` 存放在同一输出路径。
- CHECK 清单覆盖 Gate 1 至 Gate 6，且每个 Fail 或有条件通过项均能追溯到问题记录或遗留批准。
- 实际操作步骤能够支持后续人员复现本次需求生成过程。

### 5.8 步骤八：SRS 评审与基线

目标：形成可进入 SDD 的 SRS 基线。

评审输出应包含：

- SRS 文档评审结论。
- 门禁 checklist 结果。
- 实际操作步骤记录。
- SRS CHECK 清单。
- 问题清单与关闭状态。
- 开放项清单与遗留风险批准状态。
- SDD 输入充分性结论。
- 追溯矩阵入口。

SRS 进入 SDD 的最低条件：

- 所有高影响开放项已关闭，或经评审批准遗留。
- 每条需求均有来源、ASIL/QM、验证方式和验证阶段。
- 所有有效输入均已覆盖或说明不适用。
- 模块职责、接口、状态、配置、错误类别、硬件约束、安全边界和验证策略明确。
- SDD 不需要自行补充未定义的软件行为。

## 6 质量原则

### 6.1 来源驱动

每条需求必须能追溯到明确来源。无法从输入资料推导出的内容不得写成确定性需求。

### 6.2 单一可验证

每条需求只描述一个主要行为或约束，并能够通过 Review、Analysis、Test 或 Inspection 验证。

### 6.3 通用化与配置分离

FC 需求应描述模块通用职责、稳定接口语义和可配置边界。项目一次性适配应作为配置约束、Callout 适配或集成前提处理。

### 6.4 状态语义清晰

涉及模式或状态读取时，应明确区分：

- 软件请求状态
- 软件记录状态
- 硬件确认状态
- 状态不可确认

不得把“软件已请求”描述为“硬件已确认”。

### 6.5 不越级设计

SRS 描述对外可见行为和约束，不描述内部函数流程、局部变量、代码结构和测试步骤。

## 7 与下游 SDD 的接口

SRS 交付给 SDD 前，应至少明确以下内容：

| SDD 输入项 | SRS 要求 |
| --- | --- |
| 模块职责 | 明确模块做什么、不做什么 |
| 对外接口 | 明确接口能力、参数、返回语义、调用约束 |
| 模式/状态 | 明确状态集合、状态语义和转换约束 |
| 配置项 | 明确配置范围、默认值、配置时机和校验规则 |
| 硬件约束 | 明确引脚、寄存器、外设、供电、时序等软件相关约束 |
| 错误类别 | 明确参数错误、配置错误、状态错误、硬件错误等边界 |
| 多实例 | 明确实例 ID 范围、隔离要求和无效实例行为 |
| 多核 | 明确核访问权限、多核支持边界和当前内核未使能行为 |
| 安全边界 | 明确 QM/ASIL、功能安全机制来源和失效响应边界 |
| 验证策略 | 明确验证方式、验证阶段和建议验证项 |
| 追溯入口 | 明确来源到 SRS、SRS 到下游设计和测试的接入方式 |
| 通用化边界 | 明确通用能力、配置裁剪能力和集成环境约束 |

## 8 禁止行为

FC SRS 编写过程中不得出现以下行为：

- 无来源支撑地新增功能。
- 将芯片所有能力自动写成软件必须支持能力。
- 将项目一次性适配写成 FC 通用需求。
- 使用“尽量、合理、适当、快速、稳定”等不可验证表述。
- 用未确认结论替代开放项。
- 把 SDD/SDS/代码实现细节写入 SRS。
- 删除或复用已进入评审/追溯的需求 ID。
- 用 N/A 掩盖遗漏，N/A 必须说明理由。

## 9 推荐评审结论格式

```text
SRS评审结论：通过 / 有条件通过 / 不通过

输入来源完整性：通过 / 不通过
来源覆盖与追溯：通过 / 不通过
需求内容完整性：通过 / 不通过
需求质量：通过 / 不通过
SDD输入充分性：通过 / 不通过
基线发布条件：通过 / 不通过
实际操作步骤：已生成 / 未生成
SRS CHECK清单：已生成 / 未生成
输出路径一致性：通过 / 不通过

遗留开放项：无 / 有，已批准 / 有，未批准
是否允许进入SDD：是 / 否
评审人：
日期：
```

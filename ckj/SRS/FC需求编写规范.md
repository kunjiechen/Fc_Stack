# FC需求编写规范

## 1 目的

本文档用于规范 FC（Function Component）软件需求规范（SRS）的编写方法，确保需求满足汽车电子软件开发的规范性、可验证性、可追溯性，并能够作为软件架构设计（SDD）的完整输入。

FC 是独立的软件模块，应具备可移植、可配置、可复用的特性。SRS 编写应面向模块通用能力和稳定接口语义，而不是面向某一个具体项目的一次性适配实现。

本文档适用于 MCAL、BSW、IoExtDrv、ASW 等层级中 FC 模块的软件需求编写、评审和维护。

---

## 2 基本原则

### 2.1 需求层级原则

SRS 应描述模块对外可见的软件行为、接口语义、输入输出、配置项、约束、异常处理和验证要求。

### 2.1A FC 通用化原则

FC 是独立的软件模块，需求编写应优先描述模块的通用职责、可配置边界和稳定接口语义，使其能够在不同 ECU、不同 SoC、不同板级连接关系和不同项目集成环境中复用。

SRS 不应把某一次项目集成时的临时约束、单一板级接线方式、单一任务调度方式或单一项目命名约定，直接固化为 FC 的通用需求，除非该内容本身就是模块的正式上游需求或标准约束。

若某项行为仅在特定集成环境下成立，应明确其为集成约束、配置约束或使用前提，而不是将其写成无条件的 FC 通用能力。

### 2.1B 移植性与配置分离原则

SRS 应区分以下三类内容：

- 模块固有职责和对外行为
- 可配置能力、可裁剪能力和配置范围
- 集成环境提供的外部条件或依赖

需求应保证：在不改变模块职责和接口语义的前提下，FC 可通过配置、Callout 适配或集成约束接入不同项目，而不是通过修改需求定义去适配单一项目。

### 2.1C 非项目化表达原则

SRS 中应避免使用仅对某一具体项目成立的表达，例如“当前项目固定如此”“本项目不需要所以不支持”“按某板硬件接法处理”等。

推荐改写为：

- “当前版本 FC 不对外支持该能力”
- “该能力是否启用由配置决定”
- “该行为依赖集成环境提供的外部条件”
- “该差异应通过 Callout 或配置适配处理”

SRS 不应描述以下内容：

- 具体代码实现细节
- 内部局部变量、私有函数流程
- 未经来源支持的功能扩展
- 测试用例详细步骤
- 软件架构分解方案，除非该内容是上游需求或芯片手册直接约束

SRS 可以描述以下架构输入：

- 外部接口和接口语义
- 状态/模式集合和状态语义
- 配置项范围和配置时机
- 硬件引脚、寄存器或外设行为对软件的约束
- 错误类别和异常处理边界
- 时序、资源、并发、多核、多实例约束
- 安全等级和安全边界

### 2.2 来源驱动原则

每条需求应能追溯到明确来源，例如：

- 原始开发需求
- 客户需求或系统需求
- 芯片 datasheet / reference manual / user manual
- AUTOSAR、ISO 26262、MISRA C 等标准
- 平台约束、产品线约束或通用架构约束
- 可复用 FC 模块的公共接口或集成约束

若某项内容无法从来源推导，应标记为 SDD 待定、系统待定、集成待确认或配置待确认，不得编造确定性行为。

### 2.3 单一可验证原则

每条需求应只描述一个可验证的软件行为或约束。

推荐写法：

> 模块应在 `[前置条件]` 下，当 `[触发条件]` 时，基于 `[输入]` 执行 `[行为]`，并产生 `[输出/状态]`。

避免写法：

- 模块应尽量稳定运行。
- 模块应合理处理错误。
- 模块应支持多种功能并保证性能良好。
- 模块可以根据情况进行处理。

### 2.4 强制性措辞原则

需求中应使用明确措辞：

| 词语 | 含义 | 使用建议 |
| --- | --- | --- |
| 应 | 强制要求 | SRS 主体需求使用 |
| 不得 | 禁止行为 | 约束、安全、异常处理使用 |
| 应能够 | 功能能力要求 | 功能和接口能力使用 |
| 可 | 可选能力 | 仅用于明确可选配置或设计选择 |
| 建议 | 非强制说明 | 不应用作需求正文 |
| 可能 | 不确定事实 | 仅用于说明外部条件，不能作为验证结论 |
| TBD | 待确定 | 必须在评审中闭环 |

## 3 SRS 推荐结构

FC 模块 SRS 推荐包含以下章节：

1. 目的
2. 适用范围
3. 定义和缩写
4. 概述
5. 软件需求
6. 非功能需求
7. 约束与假设
8. 需求追溯
9. 验证策略
10. SRS 评审检查清单
11. 附录A 需求条目清单
12. 支持/相关性文件

### 3.1 支持/相关性文件位置

支持/相关性文件章节应放在文档最后。

文件名称应只写文档名称，不写绝对路径。若需要路径，应在文档索引或追溯文件中维护。

## 4 需求编号规则

### 4.1 编号格式

推荐格式：

```text
SRS-[FC_SHORT_NAME]-[CATEGORY]-[NNNN]
```

示例：

```text
SRS-TJA1043-FUNC-0001
SRS-TJA1043-INTF-0001
SRS-TJA1043-CFG-0001
```

### 4.2 需求类别

| 类别 | 含义 | 示例 |
| --- | --- | --- |
| FUNC | 功能需求 | 模式控制、数据处理、状态读取 |
| INTF | 接口需求 | API、信号、回调、端口 |
| CFG | 配置需求 | 实例数、开关、参数范围 |
| INIT | 初始化/去初始化需求 | 默认状态、重复初始化、DeInit |
| MODE | 模式/状态需求 | 运行模式、状态机语义 |
| DIAG | 诊断需求 | 错误检测、状态标志、DET/DEM 边界 |
| SAFE | 安全需求 | ASIL/QM 边界、安全响应 |
| ERR | 异常/边界需求 | 参数错误、越界、无效状态 |
| TIM | 时序/性能需求 | 周期、响应时间、稳定时间 |
| RES | 资源需求 | ROM、RAM、Stack、CPU Load |
| COMP | 合规/可维护性需求 | MISRA、AUTOSAR、可追溯性 |

### 4.3 编号稳定性

需求 ID 一旦进入评审或下游追溯，应保持稳定。

不得因排序、文字优化或章节移动随意重编号。删除需求时，应在追溯文件中记录废止状态，不建议复用原 ID。

---

## 5 第五章“软件需求”写法

每个需求小节应先给出精简汇总表，再逐条给出详细属性表。

### 5.1 汇总表字段

推荐字段：

| 字段 | 说明 |
| --- | --- |
| 需求ID | 唯一编号 |
| 需求标题 | 简短标题 |
| 简介 | 一句话概括 |
| 来源 | 需求来源 |
| ASIL | QM/ASIL 等级 |
| 验证方式 | Review/Analysis/Test/Inspection |
| 验证阶段 | UT/IT/ST/SDD/Coding |
| 状态 | Draft/Review/Baselined/Deprecated |

汇总表应精简，不建议放入过长描述。

### 5.2 详细需求属性表字段

每条需求应包含以下字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 需求ID | 是 | 唯一编号 |
| 需求标题 | 是 | 简明描述需求主题 |
| 需求描述 | 是 | 使用“应/不得”描述可验证行为 |
| 需求来源 | 是 | 原始需求、手册章节或标准 |
| ASIL等级 | 是 | QM/ASIL A/B/C/D |
| 前置条件 | 是 | 需求成立前应满足的条件 |
| 触发条件 | 是 | 触发需求行为的事件 |
| 输入 | 是 | 输入参数、信号、配置或状态 |
| 输出 | 是 | 输出参数、信号、状态或返回值 |
| 异常/边界条件 | 是 | 无效参数、边界值、异常状态 |
| 验证方式 | 是 | Review/Analysis/Test/Inspection |
| 验证阶段 | 是 | UT/IT/ST/SDD/Coding |
| 状态 | 是 | Draft/Review/Baselined/Deprecated |

### 5.3 功能需求写法

功能需求应回答：

- 模块应提供什么能力？
- 对哪些实例或对象生效？
- 输入是什么？
- 输出或状态变化是什么？
- 不支持的能力如何处理？

示例：

> 模块应能够控制每个已配置实例在 Normal、Standby、Sleep 三种对外支持模式之间进行模式转换。

### 5.4 接口需求写法

接口需求应明确：

- API 名称或待定命名规则
- 输入参数
- 输出参数
- 返回值语义
- 调用前置条件
- 成功后置条件
- 失败后置条件
- 是否同步执行
- 是否可重入

若 API 名称未最终确定，应在 SRS 中描述接口能力，并要求 SDD 固定命名和签名。

### 5.5 配置需求写法

配置需求应明确：

- 配置项名称
- 默认值
- 有效范围
- 配置时机：Pre-Compile / Link-Time / Post-Build
- 配置无效时的行为
- 配置项之间的一致性约束

### 5.6 模式/状态需求写法

模式需求应明确：

- 对外支持模式集合
- 芯片/硬件物理模式集合
- 软件请求状态和硬件确认状态的关系
- 状态转换条件
- 非支持模式处理

若硬件无法可靠反馈物理模式，应明确 `GetMode` 返回”软件请求模式”或”硬件确认模式”，不得模糊描述为”读取当前模式”。

### 5.7 诊断需求写法

诊断需求应明确：

- 检测对象
- 检测条件
- 状态读取方式
- 上报机制边界
- 是否要求 DEM/DTC
- 是否仅要求返回错误码

若原始需求未要求完整 DEM/DTC，不应在 SRS 中强制生成完整诊断事件体系。

### 5.8 异常处理需求写法

异常处理需求至少应覆盖：

- 未初始化调用
- 实例 ID 无效
- 参数为空
- 模式无效
- 配置无效
- 当前内核未使能
- 时序未满足
- 硬件状态不可确认

## 6 第六章“非功能需求”写法

非功能需求也应采用“汇总表 + 逐条详细属性表”的结构。

### 6.1 时序与性能需求

应明确：

- 接口同步/异步
- 响应时间
- 轮询或等待策略
- 硬件稳定时间
- 状态转换保持时间
- 是否允许阻塞

### 6.2 资源需求

应明确：

- ROM 预算或评估要求
- RAM 与实例数量关系
- Stack 使用约束
- CPU Load 约束

若当前无法给出数值，应写成“集成阶段应评估并记录”，不得编造阈值。

### 6.3 可靠性与鲁棒性需求

应明确：

- 非阻塞要求
- 状态一致性
- 配置一致性
- 并发访问或多核约束
- 错误后状态保持要求

### 6.4 合规与可维护性需求

应明确：

- MISRA C:2012 合规
- AUTOSAR Classic 约束
- 编码规范
- 命名规范
- Memory Map
- 需求-设计-代码-测试可追溯性

---

## 7 汽车电子需求质量检查清单

### 7.1 单条需求检查

每条需求应满足：

- 是否只有一个主要行为？
- 是否使用“应/不得”？
- 是否能测试或评审？
- 是否有明确输入？
- 是否有明确输出？
- 是否有前置条件？
- 是否有异常/边界条件？
- 是否有来源？
- 是否有 ASIL/QM 等级？
- 是否能追溯到 SDD/代码/测试？

### 7.2 文档级检查

SRS 文档应满足：

- 是否覆盖所有原始需求？
- 是否覆盖关键 datasheet 约束？
- 是否明确不支持范围？
- 是否避免设计实现过细？
- 是否足以作为 SDD 输入？
- 是否没有未经来源支持的功能？
- 是否没有互相矛盾的模式或接口语义？
- 是否无“优先级”等非必要字段，除非组织流程明确要求？
- 是否无绝对路径依赖？
- 是否区分模块通用能力、配置能力和集成环境约束？
- 是否避免把某一具体项目的一次性适配写成 FC 通用需求？
- 是否保证模块需求在迁移到不同项目时仍可成立，差异通过配置或集成适配解决？

## 8 SRS 到 SDD 的交付要求

SRS 输出给 SDD 前，应至少明确以下内容：

| 输入项 | 要求 |
| --- | --- |
| 模块职责 | 明确模块做什么、不做什么 |
| 对外接口 | 明确接口能力、参数、返回语义 |
| 模式/状态 | 明确状态集合、状态语义和转换约束 |
| 配置项 | 明确配置范围、默认值和校验规则 |
| 硬件约束 | 明确引脚、时序、电源、外设行为约束 |
| 错误类别 | 明确错误类型和失败后置条件 |
| 多实例 | 明确实例 ID 范围和隔离要求 |
| 多核 | 明确内核数量和访问权限要求 |
| 安全边界 | 明确 QM/ASIL 和安全机制边界 |
| 验证策略 | 明确验证方式和验证阶段 |
| 追溯入口 | 明确后续追溯矩阵接入方式 |
| 通用化边界 | 明确哪些是 FC 通用能力，哪些是配置裁剪能力，哪些是集成环境约束 |
| 移植适配策略 | 明确跨平台、跨 ECU、跨项目差异应通过配置、Callout 或集成约束解决 |

## 9 常见问题

### 9.1 芯片支持的能力是否都要写成软件需求？

不一定。

只有当芯片能力会影响软件对外行为、接口语义、配置、诊断、状态机、时序或安全约束时，才应写入 SRS。

例如：芯片支持 Listen-only 模式，但当前版本 FC 不对外支持，则 SRS 应写“不得对外支持 Listen-only”，而不是写成软件必须实现 Listen-only。

### 9.2 无法确认硬件真实状态时怎么写？

应区分：

- 软件请求状态
- 软件记录状态
- 硬件确认状态
- 状态不可确认

不得把“软件已请求”写成“硬件已确认”。

### 9.3 原始需求太简短怎么办？

可以从 datasheet、平台约束、产品线约束和汽车电子通用规范中补充可推导需求，但必须保留来源。

无法推导的内容应标记为 SDD 待定、系统待确认、集成待确认或配置待确认。

---

## 10 推荐评审输出

SRS 评审后应输出：

- 已基线化的 SRS 文档
- 需求问题清单或评审记录
- 待 SDD 固化项列表
- 需求追溯矩阵入口
- 验证策略确认结果
